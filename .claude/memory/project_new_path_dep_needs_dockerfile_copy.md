The edge image build flattens the workspace into a build context, so each path-dep crate referenced by `doorway/doorway-service/Cargo.toml` or `elohim/elohim-storage/Cargo.toml` needs TWO things in the respective Dockerfile: (1) a `COPY <crate-path> ./<flattened-path>` line, and (2) a `sed -i 's|path = "../../<crate>"|path = "<crate>"|' Cargo.toml` path-rewrite. The two Dockerfiles use DIFFERENT relative prefixes — `doorway/doorway-service/Dockerfile` rewrites `../../…`, `elohim/elohim-storage/Dockerfile` rewrites a single `../`.

When a NEW path-dep crate lands (e.g. `elohim-peer-fabric`, added 2026-06-20), BOTH Dockerfiles break with `failed to read /<crate>/Cargo.toml` and the edge build fails before any stage of value.

**Why:** it's caught LATE — the orchestrator only dispatches the edge pipeline on `dev` (and `claude/*`), so a `feat/*` or `sprint/*` push that adds the crate never triggers an edge build (see [[project_sprint_branch_not_orchestrator_indexed]]); the gap surfaces only when the change reaches dev. Recurring class: the same missing-COPY shape bit edge-#1007.

**How to apply:** whenever a Rust workspace change adds a path-dep to doorway-service or elohim-storage, grep both Dockerfiles for the existing crate COPY/sed pattern and add a matching pair before it reaches dev. When a shipped Rust workspace change won't build on edge, check Dockerfile COPY/sed coverage FIRST. Fix reference: commit 72a623439 (peer-fabric staged into both contexts; edge build went green after).

**Workspace-inheritance variant (2026-06-25, edge #1113 — elohim-render added to storage for the SSR `ssr` feature):** a path-dep crate that uses **workspace inheritance** (`edition.workspace = true`, `deno_core.workspace = true`, `serde.workspace = true`, …) needs a THIRD thing in `elohim/elohim-storage/Dockerfile`, beyond the COPY + path-rewrite: a `sed -i -e 's|<field>.workspace = true|<field> = "<concrete>"|' <crate>/Cargo.toml` block that **inlines every inherited field to a concrete version** — because the storage build does NOT copy the workspace root (`elohim/Cargo.toml`); it inlines per-crate (see the existing `constitution`/`epr`/`elohim-compute` blocks). Without it, cargo aborts at **metadata time** (0.5s, before any compile/network — so it's unmistakably code-red, not env): `failed to parse manifest at /app/<crate>/Cargo.toml → error inheriting 'edition' from workspace root → failed to find a workspace root`, exit 101 at the `Build Storage` stage. This fires **even for the lean build that doesn't activate the optional dep**, since cargo resolves the optional dep's manifest regardless. The doorway image is unaffected (its Rust builder already resolves the crate). Concrete versions come from `elohim/Cargo.toml` `[workspace.dependencies]`. Fix reference: commit f4ee77cf2 (elohim-render workspace-field inline; verified edge FAILURE #1113 → UNSTABLE #1114). The fix also lives as an inline comment in the storage Dockerfile at the elohim-render sed block. Checklist for a workspace-inheriting path-dep: COPY + path-rewrite **+ workspace-field inline**, and the crate's own transitive path-deps copied too (⚠ this last clause bit us next — see below).

**Transitive-dep + manifest-watch variant (2026-06-26, edge #1116→#1118 — `elohim-chrome-asset` gained as a dep of `elohim-render`):** the day after the elohim-render arc above, render gained a path-dep on a NEW crate `elohim-chrome-asset` (`elohim-render/Cargo.toml:11: path = "../elohim-chrome-asset"`). Because BOTH the doorway image (doorway→render) and the storage image (storage→render, and storage→chrome-asset directly) bake render, BOTH Dockerfiles broke at cargo resolve (`failed to read /app/.../elohim-chrome-asset/Cargo.toml`). Three compounding traps made this a multi-hour shake-out:
- **Transitive deps count.** A crate you never name in doorway-service/Cargo.toml still needs a COPY if a crate you DO depend on names it. `cargo tree -i <crate>` proves the chain (chrome-asset ← render ← doorway). Don't trust "doorway doesn't depend on it."
- **The two Dockerfiles use DIFFERENT layouts** (this corrects the "flattens" framing above): `elohim/elohim-storage/Dockerfile` FLATTENS (`COPY elohim/<crate> ./<crate>`, sed `../<crate>`→`<crate>`, and DOES need the workspace-field inline because it does NOT copy the workspace root). `doorway/doorway-service/Dockerfile` PRESERVES the `elohim/` prefix (`COPY elohim/<crate> ./elohim/<crate>`) AND copies `elohim/Cargo.toml` — so a transitive crate there needs ONLY the COPY: its `../<crate>` path is already correct in the elohim/ layout, and it inherits from the copied workspace root (no sed, no inline). chrome-asset fix refs: storage `3c81cd5a9` (COPY+sed+inline), doorway `49ffbd370` (COPY only).
- **Build ORDER masks a correct fix.** The edge pipeline builds doorway BEFORE storage. A correct storage-only fix looks like it "didn't work" because the doorway build dies first and aborts the pipeline at ~40s. Read the FAILING build's actual error path (`/app/elohim/...` = doorway layout vs `/app/...` flat = storage) to know WHICH build you're in.
- **THE manifest watch-path gap (the real time-sink, principle-7).** `elohim/holochain/build-manifest.json` `cargo-build-doorway.inputs.sources` watched doorway-service src/Cargo.toml/lock/client but NOT `doorway/doorway-service/Dockerfile` — while `cargo-build-storage` DID watch `elohim/elohim-storage/Dockerfile`. So the storage Dockerfile fix routed and built, but the doorway Dockerfile fix was committed-and-pushed yet routed to NOTHING (orchestrator: "0 routed, 1 skipped of 1 changed files") — NO edge build ran for an hour. A Dockerfile is build-relevant; its task MUST watch it. Fix: `f3c1b34dd` adds the watch-path (pushed with `[build:edge]` to force-validate). **When a committed CI fix never triggers a build, check the manifest `sources` globs before assuming infra/webhook trouble.** Validated edge FAILURE #1117 → UNSTABLE #1118 (chrome-asset compiled clean in both images, pushed to harbor; remaining UNSTABLE = alpha-cluster deploy-rollout, env not code). STILL-OPEN broader gap (backlog): neither edge task watches the transitive crate SOURCES (`elohim-render/**`, `elohim-chrome-asset/**`) — a source-only change to those rebuilds neither image.
