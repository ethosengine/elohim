# Residual conductor CPU after the FK-787 cure

**Residual cost, ranked by summed slow-statement seconds (Loki, 20 min, susan new vs matthew old).** The same shapes appear on both images:

1. `SELECT … FROM Action WHERE author = ? AND record_validity = ? ORDER BY seq ASC`: the full source chain per call (`rows_returned=33608`, ~8 s). 3. `SELECT cg.action_hash, cg.cap_access, cg.tag … CapGrant`: fixed by fork `61565f320` ("authorise a zome call in one query per access class, not 3N+"), also in the unbisected range.

After the FK fix every authored op is republished every `min_publish_interval` (5 min) forever. Unverified at fleet scale: measure the publish-cycle cost before designing. Candidate designs: cap required receipts at the number of reachable authorities, or back off republishing exponentially.

Read from the fork (`crates/holochain_state/src/dht_store.rs`, `record_published_op_hashes`): a chunk whose transaction fails is retried one op per transaction, and each op that fails again is skipped with one warning. A lock loss is not a fact about an op. Under a held write lock every op in the chunk fails the same way, so one refusal becomes a chunk's worth of refusals and log lines; and a skipped op has no publish time recorded, so the publish loop selects it again on its next pass. That is the perpetual republish this entry names, entered through lock contention, on the node with the most to integrate after a restart. `try_record_publish_times` opens its transaction with a plain `begin()`.

Fix shape (fork change, then a pin move and a conductor image, so an operator push): treat `SQLITE_BUSY` from the chunk as a database-level outcome (one line, leave the batch for the next pass with a backoff) instead of descending to per-op retries; and open that write transaction so it waits for the lock. Probe: after a roll, the publish-time line on adam's conductor stays under 100 in the first 90 minutes, and a genesis build started 25 minutes after the roll reads adam's custody row.

**FIXED IN THE FORK 2026-10-06 (pin moved; awaiting the conductor image and a roll):** fork `c916eddbe` (`fix/publish-time-lock-deferral`, one commit on `3c1e80525`). The recording transaction opens with `BEGIN IMMEDIATE`, so the wait for the lock happens once and before anything is written. A refused lock, at open or at a write, leaves the rest of the batch unwritten with one warning (`the database write lock was not available; publish times left for a later publish run`) and is counted in the returned outcome; per-op retries remain for failures that belong to an op. A deferred op from a sweep waits for the next sweep, so the retry interval is `min_publish_interval` and not the next trigger.
