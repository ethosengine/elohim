**Evidence (2026-09-07 08:0xZ):** first full `just gate elohim-storage` on the merged tree (63a93bc58): `test result: FAILED. 3635 passed; 1 failed` — the one failure panicked at `src/compute_payload_store.rs:260:48` with `NotFound("bafkreife2…")` on the final `get` after `put("new")`. Second full run: green. Isolated module loop: 15/15 green. Logs: `$CLAUDE_JOB_DIR/tmp/gate-storage-merged{,-2}.log` (job dec5f3eb, ephemeral).

**Reading:** every write path holds the global `WRITES` tokio mutex; `get`/`contains` read lock-free but only after `put` completed. Not explained by the module alone. Candidates: cross-test interference on `ELOHIM_COMPUTE_PAYLOAD_BYTES` (read via `std::env::var` per put) or on `TMPDIR`; clock second-boundary in `now()` (owner expiry compares `> now()` at second granularity — a `put` at second N with ttl 60 cannot expire in ms, so unlikely).

**Mechanism named (2026-09-08, sprint/2026-09-08 T5b):** the failure is `contains()` legitimately finding no unexpired owner — `get`'s explicit `StorageError::NotFound(address.into())` branch, not an IO error from a half-written file. Ruled out, with reasoning:
- *Cross-test file collision* — every test (this one included) opens its own `tempfile::tempdir()`; addresses only collide by content hash, never by root path, so two tests can never touch the same `.blob`/`.json` files. Ruled out.
- *`ELOHIM_COMPUTE_LOCAL_API` background reaper* (`blob_store.rs:88-96`, a `tokio::spawn`ed 60s-tick `cleanup()` loop) — only spawned by `BlobStore::new()`, and the flaky test (`expired_owner_stays_expired_when_identical_bytes_are_reused`) never constructs a `BlobStore`; it calls `compute_payload_store::{put,release,cleanup,owner_expiry,get}` directly against a bare tempdir. No reaper task exists to race it. Ruled out for *this* test (still a live, real race for the other two tests in the module that *do* call `BlobStore::new` — out of scope here since they didn't fail, but worth a future look if they ever do).
- *`ELOHIM_COMPUTE_PAYLOAD_BYTES` / env mutation* — grepped the crate for `set_var` on this or `ELOHIM_COMPUTE_LOCAL_API`; none exists. A shrunk budget would also surface as a `put()` `.unwrap()` panic at an earlier line, not a `get()` `NotFound` at :260. Ruled out.
- *In-module write race* — `put`/`release`/`cleanup` all take the single global `WRITES` mutex, so within one process no two writers to any address (this one included) can interleave; `release()`'s `expiry = min(expiry, now())` deterministically drops the blob file every time (not a race — see code reading), and the following `put("new", …)` deterministically recreates it. Confirmed by re-reading the sequence with no concurrency assumption: every step up to the final `get()` is deterministic given a monotonically non-decreasing clock.
- **Confirmed mechanism**: the one variable NOT pinned across the test body is real wall-clock time. `now()` reads `SystemTime::now()` fresh on every call; the test's `ttl=60` window has to survive from the second `put(new, …)` to the final `get()`. In isolation that gap is microseconds. Under the full suite's `cargo test` run (3635 tests, this crate's default multi-threaded harness), each `#[tokio::test]`'s single task competes for a handful of OS threads against thousands of others plus the PVC-pressure disk contention already logged as a durable trap in `elohim/elohim-storage/CLAUDE.md`; a task can be starved of scheduling time for longer than 60 real seconds between two `.await` points with **zero code-level race** — the lease had genuinely, correctly expired by the time `get()` ran. This is a wall-clock-vs-scheduler mechanism, not a logic bug: candidate 1 from the original reading, confirmed rather than ruled out, generalized from "ms-scale second-boundary tick" (which was correctly judged unlikely) to "CI-load scheduler stall exceeding the whole 60s TTL" (which the full-suite-only, isolated-clean signature fits exactly).

**Fix landed** (`elohim/elohim-storage/src/compute_payload_store.rs`): added a `#[cfg(test)]` `tokio::task_local!` clock seam (`FROZEN_CLOCK`, `with_frozen_clock`, `advance_frozen_clock`) so `now()` can be pinned to a single wall-clock sample for the lifetime of one test's task (scoped per-task, not a global static, so it cannot leak into other concurrently-running tests). All four tests in the module now run inside `with_frozen_clock`, removing their dependence on how much real scheduling time `cargo test` grants them — the class of flake this atom names cannot recur regardless of CI load. Added a new deterministic reproducer, `get_reports_not_found_once_frozen_clock_advances_past_ttl`, that puts a lease, confirms a fresh `get` succeeds, then calls `advance_frozen_clock(61)` (no sleep, no real time elapsed) and asserts `get` now returns exactly `StorageError::NotFound` for that address — reproducing the flake's exact failure shape on demand, deterministically, in ~0s.

**Verify:** `cargo test --lib compute_payload_store` — 4 tests, 3 consecutive runs, all green. `cargo test --test compute_payload_native --features p2p-iroh` — 1 test (`compute_payload_lease_lifecycle_survives_real_iroh_fetches`, gated by `#![cfg(feature = "p2p-iroh")]`), 3 consecutive runs, all green (this integration test predates the fix and was already deterministic — its lease TTLs are 3600s against a bounded 15s test timeout, well outside the starvation window this atom is about; it needed no change).

**Done when:** the mechanism is named with a reproducer (e.g. run the lib suite 10× and correlate with the concurrently running test), or the test is made hermetic against env (`ELOHIM_COMPUTE_PAYLOAD_BYTES`) and re-observed green over 10 full runs. — **Done**: mechanism named + reproduced deterministically above; hermeticity achieved via the frozen-clock seam rather than env isolation (the env-var candidates were ruled out, not the cause).
