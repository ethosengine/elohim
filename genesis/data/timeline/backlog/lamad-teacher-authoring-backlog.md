## What this is
The operator asked that recomposing *Foundations for Christian Technology* v2 into EPR atoms also
measure how easy or hard that authoring is, and treat improving lamad as fair game. Each row is a
place a teacher (or the agent standing in for one) had to work around lamad rather than with it.
Fixed rows say where; open rows say what the fix would be.

## F16 design — P2P design gate (2026-09-27)

### Entity: authored content edge (typed relationship between lamad atoms, with a role)
- **Classification**: Linked (A2), carried *inside* the source atom's signed entry (`Content.metadata_json` → `relationships[]`), not as a Holochain Link and not as the unused DHT `Relationship` entry. An authored edge has no meaning without its source atom and is part of what the author said the atom *is*. Computed edges stay Ephemeral (C) and are never stored.
- **Why not a Link or the `Relationship` entry**: both are separate DHT ops that ignore the atom's reach. `Relationship` is declared "always public", so an intimate love map's edges would leak. Both also need a separate delete when the author drops an edge. Inside the entry, edges version, travel and disappear with the head that states them.
- **Head-Plane Cost**: zero new heads, Kad records or conductor round-trips; edges ride the source atom's existing head. Count: ~400 edges for FCT Movement I today; order 10⁴ corpus-wide at one year. No bundling or sign-off needed.
- **Network Stakes**: all four stages. Edge reach equals the source atom's reach (floor-protected: an intimate atom's edges are LocalRelationship, never priced down). Projection cost is per adoption, not per sweep.
- **Address**: the edge's identity is its place in a signed source head (source id, type, target id). The SQL row id is `rel-` + sha256(source|type|target)[:32], the same on every peer (already live in the seeder). Targets are named by stable id; which head of the target applies is resolved at read time by the target's own declared head, never by recency.
- **Source of Truth**: Holochain DHT (the source atom's signed entry). The SQL `relationships` table becomes a per-peer projection, rebuildable from adopted heads.
- **Integrity Zome + DNA-hash class**: `content_store_integrity` (`Content.metadata_json` already exists; no validation limit). **DNA-hash-NEUTRAL**: no zome change at all; `update_content` already carries metadata.
- **Coordinator Zome**: none new. `content_store::create_content` / `update_content` return the atom's hashes as today.
- **Projections**: SQLite `relationships`, replaced per source on every head adoption (insert new, update role, delete dropped). Written only from the conductor-validated entry, never from sync-document fields. Automerge: n-a (not content in its own right).
- **HTTP Route**: none new. `GET /db/relationships?contentId=…` must apply the SOURCE atom's reach gate (today it applies none; same class as `security-content-head-route-bypasses-reach-gate`). `POST /db/relationships/bulk` becomes seeder scaffold to retire once the builder writes `metadata.relationships`.
- **Anti-Pattern Check**: avoids UUID identity (deterministic from the storage key), per-host authoring (no direct SQL edges as truth), granular DHT data (no per-edge entries), and cross-namespace joins (n-a).
- **SDO/RWA Test**: a doorway or aggregator sees edges only for atoms whose reach lets it see the atom. It cannot join a household's intimate graph without that household's crossing act (boundaries 2 and 6), provided the relationships read route enforces reach, which is a requirement of this design, not a follow-up.

### Concern canon (projection decision: "replace a source's edges from its adopted head")
C0 answered (edges live on the source atom) · C1 n-a (no election; follows the atom's elected head) · C2 answered (only conductor-validated entries write edges) · C3 answered (runs on each adoption) · C4 partial (a peer holding no copy of the source atom has no edges for it; it reports absence, not "no edges") · C5 answered (unsigned sync-doc fields ignored) · C6a partial (needs a per-atom edge cap; 256 proposed) · C6b answered (replace-set is idempotent) · C7 answered (the route serves only projected edges, reach-gated) · C8 partial (log inserted/removed per adoption) · C9 answered (keyed by stable source id across head moves) · C10 partial (legacy `relatedNodeIds` / top-level `relationships` read by the builder; `metadata.relationships` shape to be versioned) · C11 n-a · C12 answered (only the atom's signer states its edges; reach gate on read) · C13 n-a · C14 partial (SQL-seeded edges from today's scaffold remain until the first projected adoption replaces them). Register in `elohim/elohim-storage/seam-registry.yaml` at implementation.

### Back-fill check
1. No new coordinator call; the atom's own create/update returns the entry hash (CID) and the action hash is its anchor. No route id to reconcile.
2. `content_store_integrity`; no DNA-hash move.
3. ~10⁴ edges at one year, zero added heads, so the quiesce cost is unchanged.
