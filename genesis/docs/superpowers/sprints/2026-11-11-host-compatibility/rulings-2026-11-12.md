## H12: does an artifact's own declared reach decide who may draw it?

### What is being decided

Today a device serves an artifact only when the name of its build method is listed in
`berth.artifacts.serves`, and only to the audience listed for that name. A policy with no row
serves nothing (`elohim/eprfs/eprfs-peer/src/serves.rs:4-8`, `:124-129`). The shipped policy lists
one method, `mesh-build`, for the audience `steward`, meaning every device of the person
(`genesis/agentic/pool-policy.json:174-177`).

H12 (spec:1337) asks whether to replace that with reach carried on the record. Every `Produce`
would carry `env:reach`, derived as the narrowest reach among the build's inputs. The peer gate
would serve when the requester's relationship meets that reach. `serves` would remain only as a
list that narrows (spec:902-914).

### What it blocks

- **K12** is blocked outright (plan:203).
- **K6** in practice: shem's v2 floor is recorded, and "serving the floor to ethosengine waits on
  H12" (journal:166). ethosengine cannot link a v2 variant without that floor, because its own
  glibc declares v3 (spec:884-888).
- **K11** records `reach` as a declared gap on every `Produce` until K12 lands
  (plan:199; `elohim/eprfs/epr-cli/src/artifact/preflight.rs:236-240`).
- Later items that read reach from the record: C2 (plan:340) and the wider-reach frontier in X2
  (plan:277).

### Options

**A. Rule H12 as written.** Reach on the record decides; `serves` narrows.

- One trust act (the roster admitting a device) covers every present and future kind of artifact
  between one person's devices. No new policy row per kind (spec:909-912).
- An absent slot is read as `self` (spec:907). Every record written before K12 has no slot. So on
  the day K12 lands, each device starts serving to its siblings every artifact it holds, of every
  method, including ones no policy row names today. That is a widening for all existing records,
  made by a code change and not by a steward act. It is bounded: `self` reaches only devices the
  roster admits.
- `discloseMethod` "follows the same rule" (spec:913-914). Today the method record and the K9
  input lines are disclosed for `mesh-build` only, under a specific ruling of 2026-11-12 with its
  own covenant (`genesis/agentic/pool-policy.json:173`). Under A, the input lines of every artifact
  at `self` are disclosed to sibling devices with no row. Plan:181 already treats that as within
  the roster's trust, pending H12. Ruling A turns a per-method ruling into the default.
- The policy file stays valid unchanged (plan:205).

**B. Rule H12, with one amendment: an absent slot keeps today's behaviour.** A record with no
`env:reach` is served only when a `serves` row names its method, as now. A record that carries
`env:reach` is judged by reach, with `serves` narrowing.

- Nothing recorded before K12 changes who can draw it. Only records whose writer derived a reach
  are served by reach.
- Cost: shem's floor was recorded without the slot (journal:165-166). It must be recorded again
  after K12 to cross, or be given one policy row meanwhile.
- The code is slightly larger: two paths in the gate until old records age out.

**C. Decline H12 and add the `sysroot-pack` row.** This is the proposal withdrawn on 2026-11-11
(spec:1337; journal:106).

- It unblocks K6 today with a one-line policy change and no new code.
- It keeps the cost the spec measured: one grant per kind of artifact, re-asking a decision the
  roster already made (spec:892-898). K11 makes this worse, because a fresh workspace can now
  record projects under method names the steward has not seen (plan:197).

**D. Defer H12 and hand the floor across by another route** (for example, a file copy). This
leaves K12 blocked and leaves no record of who drew the floor. It is listed for completeness.

### Docs against code

1. **"Absent means `self`, which is today's behaviour for `mesh-build`" (spec:907) is true only
   for `mesh-build`.** For every other method, today's behaviour is "not served"
   (`elohim/eprfs/eprfs-peer/src/serves.rs:7-8`). Option A is therefore a widening for those
   records; the spec's sentence reads as if it were not.
2. **The motivating floor cannot be derived as `public` today.** The spec makes a floor `public`
   when its payloads are named by package (spec:904-906), and says a derivation that cannot
   classify an input must declare `private`, which the gate refuses to serve (spec:945-947,
   :906-907). The packer's manifest names files and CIDs, not packages; the spec lists that as a
   missing node (spec:955-958), and `elohim/eprfs/epr-cli/src/artifact/sysroot.rs` has no package
   attribution. Read strictly, K12 would label shem's floor `private` and refuse the one draw
   that motivated H12. The ruling needs to say what an unattributed floor is between one
   person's devices. `self` is the natural answer: it meets the K6 need and widens nothing
   beyond the roster. `public` would wait for the package-attribution node.
3. **The reach vocabulary has eight levels, and its order is not the enum's order.**
   `elohim/epr/src/reach.rs:18-37` declares `private, self, intimate, trusted, familiar,
   community, public, commons`. The spec's list of levels above `self` omits `intimate` and
   `familiar` (spec:915). The type deliberately has no `Ord`; comparisons must use `openness()`
   (`elohim/epr/src/reach.rs:9-14`, `:42-53`). "Narrowest input reach" in K12 has to be defined
   as the minimum `openness()`.
4. **Only one audience exists in code.** `grants` honours `steward` alone; `carrier:` parses and
   grants nothing (`elohim/eprfs/eprfs-peer/src/serves.rs:122-129`). So the ruling's effect today
   is confined to one person's devices whatever reach a record declares. Anything above `self`
   still needs the ladder the spec keeps (spec:915-918).
5. **No code derives a reach yet.** `reach` appears only as a gap name
   (`elohim/eprfs/epr-cli/src/artifact/preflight.rs:56`, `:238`;
   `elohim/eprfs/epr-cli/src/artifact/cargo_project.rs:105`). The rule "source from this
   repository is `self`" (spec:904) has no implementation to check against.

### Recommendation

Rule **B**: adopt reach on the record, keep `serves` as a narrowing list, and keep today's
behaviour for records that carry no slot. Add one sentence to the ruling: a floor whose members
are not yet attributed to packages is `self`, not `private` and not `public`.

This gives K12 its go-ahead and unblocks the K6 floor draw (after one re-record of shem's floor).
It removes the per-kind grant for everything recorded from now on. It makes no existing record
more widely drawable without a steward act.

### The strongest argument against it

The amendment keeps the two-path gate that H12 exists to remove, and it protects against very
little. The only parties who gain access under option A are devices the roster already admits,
and the spec's whole reading is that the roster's decision should not be re-asked (spec:892-898).
Every old record will also need re-recording or a policy row to cross, which is the friction
being removed, paid once more per artifact. If the steward sees admitted devices as fully
trusted for build artifacts, option A is simpler and honest.

### Ruling: H12

**Ruling:** Option B. An artifact's declared reach decides who may draw it, and
`berth.artifacts.serves` is kept as a narrowing list. A record with no `env:reach` slot keeps
today's rule: it is served only when a `serves` row names its method.

- **Reason.** One trust act per relationship replaces one grant per kind of artifact
  (spec:892-898), which K11 would otherwise multiply (plan:197). Keeping the old rule for
  slotless records means no existing record becomes more widely drawable through a code change
  alone. The argument against (a two-path gate, and one re-record per old artifact) is a real
  cost. It is paid once and is bounded by the exit criterion below.
- **Unblocks.** K12 may start (plan:203). The K6 floor draw follows once shem re-records its v2
  floor with the slot (journal:165-166). K11's `reach` gap closes when K12 lands (plan:199).
- **Conditions.**
  1. "Narrowest input reach" is the minimum `Reach::openness()`
     (`elohim/epr/src/reach.rs:42-53`).
  2. A floor whose members are not attributed to packages is `self`. It becomes `public` only
     through the package-attribution node (spec:955-958) and the licence reading (spec:915-917).
  3. An input the derivation cannot classify makes the record `private`, and `private` is not
     served to any requester (spec:945-947).
  4. The method record and input lines of a record that carries the slot are disclosed at that
     record's reach. For slotless records `discloseMethod` stays as it is.
  5. Nothing above `self` is served under this ruling. Only the `steward` audience grants in code
     (`elohim/eprfs/eprfs-peer/src/serves.rs:122-129`), and widening stays a ceremony
     (spec:915-918).
  6. A `serves` row still narrows a record that carries the slot: a method listed with an
     audience set that excludes the requester is refused even when reach allows (plan:205).
- **Exit criterion.** The slotless path is removed when no artifact this person's devices still
  hold and serve lacks the slot, or earlier if the steward says so. At that point the gate is
  option A.
- **Reversal.** Before K12 lands, withdraw this ruling and nothing has changed. After it lands,
  reverting the gate change restores method-name serving, because the policy file is not edited
  by this ruling. A single method can be closed at once, without a code change, by listing it in
  `serves` with an empty audience list.

## H13: do builds from different native compilers stay distinct variants?

### What is being decided

Whether to ratify compiler posture B, which the lane K owner ruled as a working posture on
2026-11-11 (journal:107; spec:931-938). Under B, two devices whose native compilers differ
produce two keys for the same source. The two builds share a family and join one variant set
through the conformance suite. The alternative is to make the compiler itself a pinned,
content-addressed input so the keys can match.

The fact underneath: shem's and ethosengine's `cc1` and `as` differ byte for byte (spec:931-932).
The K9 receipt confirms the link driver differs at the same path, `tool:link-driver:target`
(K9 receipt:27-32). The driver's identity and defaults are keyed
(`elohim/eprfs/epr-cli/src/artifact/host.rs:154-156`).

### What it blocks

Nothing is hard-blocked: lane K has worked under B since 2026-11-11. What depends on the answer:

- **K6's and K7's verify text.** K6 says "F2r closes with equal keys in both directions"
  (plan:159-161) and K7 re-runs the F2r fetch half "on the new key" (plan:163). Under B, keys
  from two native compilers cannot be equal. See "Docs against code".
- **Lane V** becomes the only route by which a native build on one device is reused on the other
  (V1 plan:211, V2 plan:215, V3 plan:219). None has started.
- **X1** (plan:273) names the seed's members; under option C below the compiler closure becomes
  one of them.

### Options

**A. Level the devices onto one compiler image.** Keys match because the hosts match.

- It contradicts the direction already ruled: "variety is the protocol's strength" (plan:43-44),
  and the spec's title claim, closure not image (spec:282-296).
- shem's image is an x86_64_v2 distribution because its CPU needs one (K9 receipt:22-24).
  Levelling would mean ethosengine adopting it, or shem being unable to build.

**B. Ratify posture B.** Per-compiler variants share a family, not a key.

- It needs no new mechanism, and the key stays truthful: a differing toolchain computes a
  different key (spec:349-350).
- Cross-device reuse of native builds does not come from identity hits. It comes from variant
  selection: fetch by family, admit, choose (K3, plan:147), and later from variant sets judged by
  a conformance suite (V1, V2).
- The count of variants grows with the count of distinct compilers. With two devices that is
  two. It is a real cost only at larger scale.
- The F2r receipts need restating (below).

**C. Pin the compiler closure now.** A CID-pinned gcc closure becomes a floor member, mounted
beside each device's native toolchain (spec:935-937).

- Keys match across devices without levelling either image. F2r closes as originally written.
- It is a large new artifact. It would be recorded, held and served like a floor, which today
  waits on H12. It needs a licence reading before it can travel above `self` (spec:915-917).
- It needs a compiler closure that runs on shem's v2 CPU. The floor work showed that gcc's
  support objects do not move with `--sysroot` alone (journal:166-167), so the mounting is not
  yet understood.
- It delays K6's close behind new design work, for a benefit two devices barely feel.

### Docs against code

1. **Spec §6.3 promises a key match that posture B withdraws.** Spec:337-339 says two devices on
   different images building for one declared target "use identical link inputs. Their derivation
   keys match and they share an identity hit. This closes F2r". Spec:931-933 says one floor alone
   does not make their keys equal. Both are in the same document. The code agrees with the
   second: the driver is keyed by content (`elohim/eprfs/epr-cli/src/artifact/host.rs:154-156`),
   and the K9 receipt shows the driver line differing (K9 receipt:31).
2. **K6's verify cannot pass as written under B.** "Equal keys in both directions" (plan:159-161)
   is reachable under B only when one compiler produces both builds, or after option C. If H13
   is ratified, the K6 and K7 verify lines should be restated. For example: each device records
   its own key under one family; each fetches the other's variant by family and admits or
   refuses it; and the v3-on-v2 refusal under emulation stays as it is.
3. **The spec's own ruling row already says "ruled"** by the lane K owner (spec:1338), while
   spec:1320 lists H13 as open. It is open for the steward; the working posture is in force.

### Recommendation

Ratify **B**, and in the same ruling direct that spec §6.3 consequence 1 and the K6 and K7
verify lines be restated to match it. Keep the pinned compiler closure (option C) as a named
later optimisation under X1, to be taken up when a third device or a measured variant-count
cost asks for it.

### The strongest argument against it

Under B, the only route by which the two devices reuse each other's native builds is lane V, and
none of lane V exists. Until V1 to V3 land, B means the artifact store's central promise between
these two devices, build once and reuse, is delivered only for same-compiler rebuilds. Option C
would deliver identity hits through code that already works (the key, the fetch, the holders).
It can be argued that a pinned compiler closure is less new machinery than variant sets plus a
conformance suite, and that ratifying B commits the sprint to the larger build.

### Ruling: H13

**Ruling:** Option B is ratified. Builds from different native compilers are distinct variants
that share a family and not a key, until a pinned compiler closure exists.

- **Reason.** It is what the code does and what the K9 receipt measured: the link driver is keyed
  by content and differs between the two devices (K9 receipt:27-32;
  `elohim/eprfs/epr-cli/src/artifact/host.rs:154-156`). It keeps the key truthful (spec:349-350)
  and keeps each device on its native toolchain, which the ruled direction requires
  (plan:43-44). The argument against is accepted as a schedule fact: cross-device reuse of native
  builds now depends on lane V, and the conditions below say so in the plan's own words.
- **Unblocks.** K6 and K7 can close on receipts that posture B can produce (plan:159-163). Lane V
  (plan:211-219) is confirmed as the reuse route between devices with different compilers.
- **Conditions.**
  1. Spec §6.3 consequence 1 (spec:337-339) is restated: a shared declared target gives equal
     link inputs and one family; keys are equal only when the compiler is also the same.
  2. K6's and K7's verify lines are restated to: each device records its own key under one
     family; each fetches the other's variant by family and admits or refuses it; the v3-on-v2
     refusal under emulation is unchanged. The coordinating session applies both restatements.
  3. The pinned compiler closure (option C) stays a named later optimisation under X1
     (plan:273).
- **Exit criterion.** Option C is taken up when one of these is measured: a third device or a
  third distinct compiler joins; or V1 to V3 have landed and cross-device reuse between two
  compilers still fails; or the variant count per family is shown to cost more to hold than the
  closure would.
- **Reversal.** Adopting a pinned compiler closure later is additive. Keys built against it are
  new keys in the same family, and the per-compiler variants recorded meanwhile stay valid
  members. Nothing recorded under B has to be rewritten.

## The scope of K10: how much dispatch evidence to build, and when

### What is being decided

K10 (plan:187) says the extracted ISA requirement should count only code reached without a
runtime feature check, on evidence bound to the bytes. The K10 note found that honest evidence
is much larger than the plan item implies. A function hash proves identity, not guarded
reachability. The three real mechanisms (ring's capability tokens, compiler_builtins' cached
function pointer, blake3's public platform enum) each defeat a simple branch-dominance check
(K10 note:11, :45, :51, :57-59; plan:193). The steward is asked how much of that to build now.

The measured need: an `epr` built on shem extracts a v3 requirement, yet shem's Sandy Bridge CPU
runs it. Its v3 level comes only from dispatched code. The recorded clause would refuse the host
that built and runs the binary (plan:195; journal:182-186).

### What it blocks

- Nothing refuses today. No device observes its own `Provides` until A2 (plan:123), and nothing
  calls `admit` on a real host until A3 (plan:127). The journal says the same (journal:185).
- Once A3, A4 (plan:131), P1 (plan:235) or R1 (plan:306) enforce admission, shem is refused its
  own `epr` unless K10 has narrowed the clause or an exception exists. So K10, or a decision to
  enforce without it, must come before admission is enforced on shem.
- K8's seven extras stay counted until K10 proves the dispatch (plan:177).
- V5 and S4 (plan:302, :298) rely on the clause being right in the other direction: a real
  v3-on-v2 death must still be predicted.

### Options

**A. The K10 note's minimum honest slice.** A post-link certificate bound to the whole artifact's
CID, one ELF and link configuration, the named contracts only: ring 0.17.14, compiler_builtins'
FMA selection, blake3, and both `sha2` versions (K10 note:61-63, :87-95).

- This is the smallest scope that meets K10's verify as written (plan:191). For epr on
  ethosengine, exactly v3 is the outcome, because sqlite's v3 instructions remain (plan:191).
- It is a large build: a build finalisation step, a verifier, and a pinned contract for each
  crate version, kept up as crate versions move (K10 note:27, :87).
- It does not by itself fix shem's case. shem's build also needs the `tzcnt` class removed
  (option B), and the note states it does not certify the existing artifact, because the
  compiler_builtins source snapshot is not held locally (K10 note:53, :106).

**B. The baseline-compile attestation only.** A build attestation naming the code's target
features, so `tzcnt` encodings in code compiled at baseline stop counting as `bmi1` (plan:195).

- It is small, and one mechanism covers 1,277 of the 1,281 `bmi1` sites (plan:195).
- It does not remove the dispatched `avx2`, `adx`, `sha_ni` or `fma` code, so shem's `epr` still
  extracts v3 and is still refused. It fixes the smaller of the two problems.
- It depends on the build receipt that K11 leaves as the `compiler-inputs-unattested` gap
  (plan:199).

**C. Defer narrowing; keep the extracted clause as a truthful upper bound, and let a device's own
build run on its own host.** Spec:185 already says "a device may run its own build on `declared`
and `extracted` clauses". The clause stays v3. Admission on the building device treats its own
build as admitted and records that the extracted clause was not met.

- No certificate system is built now. Admission can be enforced (A3, P1, R1) without refusing
  shem its own tools.
- A sibling at the same hardware level still cannot be offered that build: for other devices the
  clause refuses. The variant count stays inflated, which is the cost spec:174-175 names.
- It adds an exception at the admit call site that needs its own rule and record, so it cannot
  become a silent bypass. The plan says no identity exemption exists for recording (plan:199);
  an admission exemption for one's own build would be the first.

**D. The full design in the K10 note for all crates and link configurations.** It is not
proposed by anyone; the note itself scopes down to A (K10 note:61).

### Docs against code

1. **Spec §3.2 names evidence the real crates do not produce.** It allows "the compiler's
   multi-versioning resolver metadata, or a build-time attestation naming the guarded functions
   by content" (spec:170-173). The K10 note found that none of the inspected mechanisms is
   compiler multi-versioning (K10 note:45), and that naming functions by content is not enough,
   because a new caller can bypass the guard while the guarded bytes stay unchanged
   (K10 note:11, :104). If option A is chosen, spec §3.2 needs amending to the note's stronger
   wording.
2. **K10's verify names ark's blake3 `*_avx2` paths** (plan:191), but blake3's platform enum is
   public, so a guard there is not provable by annotation (K10 note:57-59). The verify line is
   achievable only with the final-program provenance check the note describes.
3. **"A device may run its own build on `declared` and `extracted` clauses" (spec:185) is false
   for shem today** if read as "admit permits it": the extracted clause refuses the building
   host (plan:195). Either the sentence means an exception at the call site (option C), or it
   assumed extraction would not overstate.
4. **The code is ready for narrowing and rejects it from callers.** `Clause.narrowing` exists and
   `admit` ignores it (`crates/elohim-host-contract/src/requirement.rs:31-37`). `put` refuses a
   caller-supplied narrowing (`elohim/eprfs/epr-cli/src/artifact/requires.rs:62-69`). ENDBR is
   the one hint-space case already listed as not required
   (`elohim/eprfs/epr-cli/src/artifact/extract_isa.rs:449-465`).

### Recommendation

Sequence it, and rule the sequence:

1. **Now: option C as a declared rule**, written into spec §3.2 and into A3's verify. A device
   may run its own build when the only unmet clause is `extracted`. The verdict records which
   clause was not met and that the build was the device's own. No other device is offered the
   build on that basis.
2. **Next: option B**, when K11's build receipt exists, because it is small and removes a whole
   class of false `bmi1`.
3. **Then: option A**, scoped exactly as the K10 note's minimum slice, started only when a second
   device at the same level needs to draw a dispatched build, or when the variant count becomes
   a measured cost. Amend spec §3.2 to the note's wording at that point.

K10 stays open in the plan with this order recorded on it. The certificate system is the right
design, but nothing running today needs it, and the one live harm (shem refused its own `epr`
once admission is enforced) has a smaller remedy that the spec already states.

### The strongest argument against it

Step 1 makes "it is my own build" a reason to run bytes whose recorded requirement the host does
not meet. That is the shape of exemption the uniform rule of 2026-11-12 refused for recording
(plan:199). The clause exists to predict an illegal-instruction death before launch; an own-build
exception removes that prediction on exactly the device most likely to hit it, for example a
build made on shem with `-C target-cpu` set wrongly. If the exception lands first and option A
keeps being deferred, the wrong clause becomes permanent and the exception becomes the real
admission rule. The alternative is to hold enforcement (A3, P1, R1) on shem until option A
exists, and accept that delay.

### Ruling: the scope of K10

**Ruling:** The sequence C, then B, then A. K10 stays open in the plan with that order. The
certificate system of the K10 note (option A) is the accepted design and is not built now.

- **Reason.** Nothing running today refuses on the extracted clause (plan:123-127;
  journal:185), so the certificate system has no present consumer. The one harm in sight is a
  device refused its own tools once admission is enforced, and the spec already states the
  smaller remedy (spec:185). The argument against (an own-build exception removes the prediction
  on the device most likely to need it, and can become permanent) is answered by making the
  exception narrow, recorded and self-withdrawing, in the conditions below.
- **Unblocks.** A3, A4, P1 and R1 (plan:127, :131, :235, :306) may enforce admission on shem
  without waiting for dispatch evidence. K8 keeps counting its seven extras (plan:177), so no
  recorded `Requires` changes.
- **Conditions for step 1 (the own-build rule).** A device may run a build whose recorded
  requirement it does not meet only when all of these hold:
  1. Every unmet clause is on the `isa.x86` axis and has source `extracted`. A `declared` or
     `proven` clause, or any other axis, refuses as before.
  2. The artifact's `Produce` was recorded by this same device.
  3. The verdict is recorded as a permit under the own-build rule, naming each unmet clause. It
     is not recorded as a plain permit.
  4. The rule does not apply to another device. A sibling is offered the build only when `admit`
     permits it on the clause as recorded.
  5. An illegal-instruction death of that artifact on that device (F3, plan:259) withdraws the
     rule for that artifact on that device.
  6. Spec §3.2 and A3's verify are amended to state this rule before any code relies on it.
- **Step 2 (option B)** starts when K11's build receipt exists (plan:199), since it needs the
  code's target features attested.
- **Step 3 (option A)** starts when one of these is measured: a second device at the same
