**Receipt ownership.** Ordinary sequential stale receipts are cleared after exclusive lock acquisition. An ordinary second live runner gets no recording slot. A builder crash after writing its receipt cannot by itself record green because the parent uses the process exit status, and an unanswered Task is ineligible. The failure is stale-lock recovery. Two contenders can both read a dead PID, then one can unlink the other’s newly acquired lock. A dead parent can also leave a builder alive with the shared receipt path. Either case allows a matching receipt from run A to authorize run B’s successful exit on different bytes. PID reuse alone has the opposite effect and suppresses recording. Task-to-direct fallback also reuses the first attempt’s receipt path without clearing it. Finally, `--only` writes the same receipt as a full run.
