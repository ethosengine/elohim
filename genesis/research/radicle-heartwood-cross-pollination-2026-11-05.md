# Radicle / Heartwood Cross-Pollination — November 2026

**[Radicle](https://radicle.dev)** is the longest-running attempt at a peer-to-peer code forge. Its current protocol, **Heartwood**, stores each repository as one bare git repository with a namespace per peer, signs each peer's whole ref set ("sigrefs"), elects canonical branches by a delegate threshold, gossips "I have this repository" announcements, and moves bytes as git packs. To us it is a **failure archive for the sprint we are about to run**. Heartwood is a working state plane: signed name-to-hash maps, threshold-elected heads, and verify-before-apply for refs. It never built a data plane for artifacts. Large data is pointed at git-annex/LFS, CI results carry no output digest, availability is whoever chooses to seed, and the only replica target is a client-side default for one sync. **The single most important lesson for the artifact sprint: a push-time replica count is not custody.** Heartwood's `DEFAULT_REPLICATION_FACTOR = 3` is a per-operation default that one fetch or announce tries to reach; nothing holds it afterwards, there is no repair loop, and a fetch that finds no seed waits for the next periodic sync tick rather than reacting when a seed appears. So a rakia channel head must not move until the artifact's whole chunk closure is held under committed custody by holders other than the publisher, **counted from evidence we can authenticate and that is still fresh**, and the reconciler, not the publish command, must keep that true. The second lesson follows from the first: our custody counts today are read from inventory rows whose holder identity the sender fills in itself (lesson 2), so the gate the first lesson asks for cannot yet be trusted.

Method: three Sonnet readers, three Codex legs, an Opus synthesis with targeted re-checks in source, then per-claim adversarial verification and three reviews (details under **Method + credit** and **Challenge pass**). **Verification key:** ✅ verified in source (re-checked or read directly) · ◐ single-source, inference, "not found in grounding", or primary web page read through a summariser · ⚠ secondary web or unverified. Abbreviations: **HW** = `genesis/research/repos/heartwood/crates/`, **CIB** = `genesis/research/repos/radicle-ci-broker/`, **R1–R4** = RIPs 0001–0004 in `genesis/research/repos/radicle-rips/`, **ES** = `elohim/elohim-storage/src/`.

**Membrane (sovereignty-frame: bounded).** Radicle presents its identity as *self-certifying*: a Node ID is an Ed25519 key, a repository's authority is a set of delegate keys plus a threshold, and the RID is the hash of a document those keys signed (R2, "Overview"). The TUF-style mechanics are sound. The ontology is not ours. R2 equates node, user and public key, and R1 says delegates "need not map one-to-one to maintainers", which concedes that the key set is not the people. We keep **ngit L1** unchanged: a signature is provenance; standing is held by people and collectives and backstopped by community; the network holds the root. Our identity ontology is *imago dei*, not crypto self-sovereignty. Radicle adds new evidence for L1 (lesson 12) without moving it. **Wherever this survey borrows a signed root, a threshold or an elected head, read it this way:** a manifest signature or an attestation signature is provenance only; "root" means the content lineage anchor (a genesis CID), never an authority root; and a head moves only through recognised standing (election and the roster home, final-by-witness under §12.10), never because a key signed.

## What Heartwood is, mechanically (only what bears on artifacts)

| Mechanism | How it works | Grade, cite |
|---|---|---|
| **Storage namespaces** | One bare git repository per RID; each peer's refs under `refs/namespaces/<nid>/…`; one shared object DB, so forks deduplicate. A peer writes only its own namespace; the remote helper refuses a push to another NID | ✅ R3:23-33, 120-137, 346-355 |
| **Sigrefs** | The signed unit is a flat `"<oid> <refname>\n"` list in BTreeMap order (`Refs::canonical`), and Ed25519 signs exactly those bytes. The sigrefs commit holds two blobs, `refs` and `signature`; commit metadata is not signed | ✅ `HW/radicle/src/storage/refs.rs:170-183`, `…/sigrefs/write.rs:327-334` |
| **Root/parent hardening** | Feature levels `None < Root < Parent` (1.8). `refs/rad/root` inside the signed map binds it to the RID (stops grafting): added in 1.1.0, required at verification only from 1.7.0. `refs/rad/sigrefs-parent` (1.7, optional) must equal the real parent commit (stops replay). The reader walks history for duplicate signatures, **detects** downgrades, and fetch enforces a **configurable** minimum feature level | ✅ `refs.rs:278-311`; `write.rs:108-113`; `read.rs` ~145-300; `CHANGELOG.md` 1.1.0, 1.7.0, 1.8.0 |
| **Identity doc + canonical refs** | The doc (delegates, threshold, visibility, payloads) is itself a COB at `refs/rad/id`; the RID is the git OID of the initial doc blob. `xyz.radicle.crefs` gives per-pattern `allow` + `threshold`. A commit's votes come from allowed tips that descend from it; candidates past threshold are kept and the longest linear chain wins. **Two over-threshold candidates with no linear relation fail with `DivergingCommits`; there is no recency tiebreak** | ✅ `HW/radicle/src/git/canonical/quorum.rs:173-237`, `error.rs:25,35`; `identity/crefs.rs:1-80` |
| **COB embeds** | Issues, patches and identity are signed commit DAGs under `refs/cobs/<type>/<oid>`. Attachments are `Embed{name, content}` stored as git blobs **inside the signed change tree**, referenced as `git:<oid>`. They travel only when the COB ref is fetched (all or nothing). No per-embed size cap was found | ✅ `HW/radicle-cob/src/change/store.rs:205-215`, `HW/radicle/src/cob/common.rs:367-399`; cap not found ◐ |
| **Gossip** | Node, inventory and refs announcements, signed and timestamped. Inventory is **repository-granular** and capped at `INVENTORY_LIMIT = 2973` RIDs per message. Above the cap the announcement is **silently truncated** for peers, with only a local warning ("other nodes will see only some of your projects"), although the doc comment says it "should be the whole inventory every time" | ✅ `HW/radicle-protocol/src/service/message.rs:27, 235`; `service/gossip.rs:38-47` |
| **Seeding + replica target** | Seeding is a per-repo `Allow{scope}`/`Block` policy, chosen by the operator; R1 rejects DHT placement because operators must choose what they host. The only replica target is client-side and per operation: `DEFAULT_REPLICATION_FACTOR = 3` is the default `must_reach` for both the fetcher and the announcer, overridable as a range (`--replicas`/`--replicas-max`). No network-wide target and no repair loop were found in `radicle-node/src` | ✅ `HW/radicle/src/node/sync.rs:14, 77`; `node/sync/fetch.rs:12-19`; `announce.rs:203, 213`; `node/policy.rs:160-169`; R1 "Topology" |
| **Fetch** | Git smart protocol (gix) over a Radicle stream. Stages: canonical `rad/id`, delegates, sigrefs, verify, data refs, validate, apply only if valid delegates ≥ threshold; several stages can transfer packs. The enforced cap is `fetchPackReceive`, **default** 500 MiB (configurable), by a byte-counting reader. Nominal 5 MiB / 5 GiB stage limits sit behind `#[allow(dead_code)]` fields | ✅ `HW/radicle/src/node/config.rs:136, 148-150`; `HW/radicle-fetch/src/state.rs:27, 30, 399, 454`; `stage.rs:197, 284, 365`. Whether the 5 GiB limit is enforced elsewhere: ◐ |
| **Objects before authorization** | Packs are integrity-verified as they are written (`pack::data::input::Mode::Verify`), but they are written **straight into the live object store** as `.keep`-held packs, **before** sigrefs and threshold authorization. Ref updates stage in an in-memory refdb and commit only after validation; objects of a rejected fetch are left for GC. No quarantine. Clone (not fetch) uses a temp repository moved into place on success | ✅ `HW/radicle-fetch/src/transport/fetch.rs:54`; `state.rs:152-168, 246-250`; `HW/radicle-node/src/worker/fetch.rs:53` |
| **CI broker job COBs** | `cib` turns node ref events into CI events in a SQLite queue, runs adapter subprocesses (a two-message JSON protocol: `Triggered{run_id, info_url}`, then `Finished{result}` with `Success`/`Failure` only), and writes **one job COB per commit** signed by the node's device key. The adapter response has **no artifact field**, and COB update failures are **logged and ignored** | ✅ `CIB/adapterlib/src/lib.rs:440-455`; `CIB/src/cob.rs:92-130`; `CIB/NEWS.md:247-249` |

## HARD-EARNED LESSONS

Ranked by consequence for the artifact sprint. Each lesson names the failure Radicle hit, the property it teaches, how it adjudicates against **our current build state**, and a sprint-testable form.

### 1. A push-time replica count is not custody; custody is a measured, continuing contract (R12 b, e)

**Failure.** Replication is a client-side, per-operation target (`sync.rs:14, 77`, the `must_reach(3)` default for fetch and announce, tunable per call) ✅. No network replica target or repair loop was found ✅. A fetch that finds no connected seed is retried only by the periodic sync task, which re-iterates seeded policies and re-attempts repositories missing from storage every `SYNC_INTERVAL` (`HW/radicle-protocol/src/service.rs:765-770`); the source admits it is not retried on the events that should trigger it, a new seed connection or a routing-table update (`// TODO: We should make sure that this fetch is retried later, either when we connect to a seed, or when we discover a new seed`, `service.rs:2544-2547`) ✅. R1 rejects compulsory placement and admits that a non-delegate contributor's patches are unavailable unless they stay online, with "no satisfactory answer at the protocol level" (R1:418-441) ✅. The FAQ's availability promise is "as long as at least one seeding node is online" ◐. Radicle has since had to propose making announce-on-init and synchronous push *off* by default (open patch, seed patch JSON :5334) ◐: publishing and advertising had run ahead of anything being held.
**Property.** Custody is a *standing commitment held by a reconciler*, distinct from the act of publishing, and a head that names unheld bytes is a dangling pointer. A custody count is only as good as its evidence: holders must be authenticated, the evidence must be fresh, and three copies in one failure domain are one copy.
**Against us.** We are ahead on mechanism and behind on wiring and evidence.
- The custody controller exists (`ES/reconcile/custody.rs:1-40`). It kicks `race_fetch` when a provider lacks a committed blob and emits `placement-gap` when a provider goes silent ✅. Salvage is opt-in with a **per-config** `target_replicas` and never conscripts (`custody.rs:397-404, 525-530`) ✅.
- A generic first-commitment producer is **built**: after verified self-placement, `distribute_shards` calls `ReaCommitmentService::ensure_active_self_custody` (`ES/p2p/mod.rs:2556-2570`; `ES/services/rea_commitment_service.rs:307`) ✅, and the backlog item `2026-07-30-custody-blob-first-commitment-auto-producer.md` is `done` ✅. What is missing is the link from build outputs to the plane: nothing in brit or rakia routes a build output (`brit build put --output <CID>`) into a store path that fires it ◐ (grep of brit and rakia). And the producer mints *self* custody, which is publisher custody; the invariant below needs commitments from others.
- `honored` custodians are counted from **fresh inventory rows** (`custody.rs:507-510`) ✅. Those rows carry a holder identity the sender declares (lesson 2), so today a spoofed advertisement can inflate a custody count.
- `custody.rs:15-21` records that gossip inventory publish dies on every pod restart (`InsufficientPeers`) ✅, so the reconciler's view of holders is weakest exactly after a deploy, and an empty inventory is not evidence of absence.
- The existing `blob-durability` habit is green on household evidence only; its fleet half is unmeasured, and six of its eight feature files are wholly `@wip` (14 runnable scenarios in 4 files) ◐ (grounding §4). The new habit below builds on a thin base.

**After re-genesis 1.** Unchanged in substance: custody-before-head is sprint 2 (plan §7.3, R3). Two inputs moved. Custody announcements are now signed and travel through both gossip stacks (`ES/p2p/custody_announce.rs:1-3`, topic `elohim/storage/custody/2`), and the household chaos lane went from refused to 3/3 on both devices (`RESULT.md`). The custody count still reads freshness-bounded inventory (`ES/reconcile/custody.rs:116, 181`), and holder identity is now bound to the transport peer but not yet to the agent (lesson 2). The alpha re-genesis added a sharper instance of the failure this lesson names: storage's binding minter gave up after six attempts because the conductors were not yet installed, and nothing retried, so no alpha node held a cross-signed binding (regression class 7). That is Radicle's "retry on the tick, not on the event" (`service.rs:2544-2547`) in our own code ✅.
**Sprint form.** *Invariant:* a rakia channel head moves only when every chunk of the artifact's manifest closure has ≥ k committed custodians other than the publisher, spread over ≥ d declared failure domains, each counted from a holder claim bound to its authenticated sender (lesson 2) and fresher than a declared TTL, with a verified fetch on record. Publishing does not announce the head before this holds. When a closure falls below k after publication, the channel shows a typed `under-custodied` state and the reconciler repairs within a bounded time; it never conscripts. *a2o:*
- "Given an artifact published to channel C by Matthew's device, when Matthew's device goes offline, then every chunk is fetchable and hash-verifies from at least two other holders, and C's head was not observed to move before that held."
- "Given a published artifact with k custodians, when one custodian is lost, then the closure is reported under-custodied and is repaired from consenting capacity within the repair budget."
- "Given too little consenting capacity, when an artifact is published, then the head does not move and the publish reports a typed shortfall; no peer is conscripted."
- "Given three custodians on one failure domain, then they count as one toward d."

### 2. A holder claim is only as good as the identity bound to it; inventory is an expiring hint, never truncated (dataplane)

**Failure.** Inventory is repository-granular and truncated at 2,973 RIDs with only a local warning (`gossip.rs:38-47`) ✅. The open issue "Smarter Inventory Announcement" reports that a capped node "may never announce a new repository it has added" ◐. In the Unreleased section, relay had to track `(subject, version, relayer)`, because peers that had relayed an older version were never sent the newer one (`CHANGELOG.md:17, 20`; `service.rs:1491-1505`) ✅. An inventory entry says "I have this repository", with no object-level knowledge (`service.rs` ~1610) ✅. And the disclosure shows what follows when a declared identity is not the authenticated one: a node passed itself off as an allow-listed Node ID ◐.
**Property.** An advertisement is a hint that expires. Any page the receiver might read as complete is versioned, paginated or reconciled, never cut. A holder identity carried inside a message must equal the identity the transport authenticated, or be signed by that holder; a hash protects the bytes, never the claim about who holds them.
**Against us.**
- **Transport authentication** ✅: libp2p gossipsub runs `MessageAuthenticity::Signed` with `ValidationMode::Strict` (`ES/p2p/behaviour.rs:521-530`). This corrects the earlier draft's "advertisements are unauthenticated today".
- **Holder identity is not bound** ✅: `handle_inventory` (`ES/p2p/gossip_dispatch.rs:410-445`) applies `snapshot.peer_id`, a field the sender fills in, after structural checks only, and never checks it against the authenticated `source`. On iroh, `source` is `delivered_from` (`ES/p2p_iroh/gossip_receive.rs:174-176`) ◐, the neighbour that passed the message on, not its author. So any participant can replace another peer's inventory or invent holdings for it, and lesson 1's custody count reads those rows. Custody announcements and salvage ads get structural checks only ◐ (grep only).
- **Payload signatures** are a **Stage-1 placeholder where one null byte is sufficient** (`ES/p2p/inventory_gossip.rs:13-18, 121, 143, 175`) ✅; no Stage-2 code appears in `p2p/inventory_*.rs` ✅.
- **Sequence**: our "version" is a per-peer `sequence` the peer declares. Without the binding above, the highest sequence wins even from a sender who is not that peer, and a forged snapshot could re-base a peer's cursor ◐ (`apply_snapshot` not read).
- **Granularity and paging are built** ✅: we advertise per blob, with snapshot plus delta and per-peer sequence gap detection (`inventory_gossip.rs:1-11`), and a full refresh is one bounded snapshot plus bounded additive deltas (`ES/p2p/inventory_broadcaster.rs:275`), with backpressured pages retried (`ES/p2p/mod.rs:4242`) ◐. Individually held shards are advertised, which keeps partial holders discoverable (shard-only inventory test, `inventory_broadcaster.rs:1067`) ◐. Whether per-chunk advertisement volume becomes a problem for multi-GiB artifacts is unmeasured.

**Implementation trap (orchestrator re-check)** ✅: the snapshot `peer_id` is the publisher's libp2p `PeerId` (`ES/p2p/mod.rs:4352` → `ES/p2p/inventory_broadcaster.rs:233`), so equality with the transport identity is well-typed. But the dispatch layer does not carry the signed author: `GossipSource::Libp2p` holds `propagation_source`, the *relaying* neighbour, "for logging only" (`ES/p2p/gossip_dispatch.rs:43-50`). The binding must compare against gossipsub's signed `message.source`, threaded through to `handle_inventory`. Comparing against `propagation_source` would refuse every relayed snapshot.

**After re-genesis 1.** Largely landed ✅. Inventory is now a signed delta envelope on `elohim/inventory/blob/2`; the snapshot message is gone; the signature covers `{body, epoch, level, holder, author_peer}`; admission requires the gossipsub-authenticated `message.source` (not `propagation_source`) to equal `author_peer`, and the signing key to be the one the transport peer embeds (`ES/p2p/inventory_gossip.rs:1-31`). A replayed delta never moves a cursor backwards, and full-state convergence is range reconciliation, `negentropy-v1`, on `/elohim/inventory-recon/1.0.0` (`ES/p2p/inventory_recon.rs:1, 33`). The v1 topic is reported unavailable, never as holding nothing (`inventory_gossip.rs:42-46`). **Still open:** the holder key is the transport key, not the agent key; cross-signed agent-to-transport bindings do not yet exist on alpha, so custody rows are bound to a peer, not to a person's standing (`RESULT.md`, follow-ups). Household evidence also showed libp2p gossipsub publishing nothing for 75 minutes (`InsufficientPeers` on every topic) while request-response and reconciliation converged ✅ (habit `dataplane-convergence` DELTA 2026-11-06): a direct confirmation that inventory gossip is a hint and reconciliation carries the truth.
**Sprint form.** *Invariants:* on libp2p, a payload's holder identity must equal the gossipsub-authenticated author (`message.source`, not `propagation_source`) or the message is refused; on iroh, where relaying hides the author, the payload carries the holder's signature; custody counts (lesson 1) come only from verified fetches and authenticated, unexpired claims; snapshot pages are never cut. *Tests:* a spoofed-holder snapshot is refused and does not change custody counts; a replayed old snapshot does not re-base the cursor; an interrupted or reordered refresh converges; a peer holding only part of an artifact stays discoverable as a source. *Design question, measured first:* whether to add manifest-level aggregation (manifest CID plus held-chunk completeness) **beside** per-blob entries; take it only if the household measurement shows advertisement volume matters, and never at the cost of partial-holder discovery.

### 3. Verify into staging, publish atomically, contain corruption (storage)

**Failure.** Heartwood integrity-checks packs while writing them (`Mode::Verify`, `HW/radicle-fetch/src/transport/fetch.rs:54`) ✅, but writes them into the live object store before the fetch is *authorized* (`state.rs:165-168`) ✅, so bytes from a rejected fetch sit in the store until GC. An open issue reports that "one corrupted Git repository makes the Radicle node unable to start" (seed issue 7298) ◐. In 1.3.1, SQLite `read` unwraps had to become `try_read` (`CHANGELOG.md:760`) ✅. Only clone got the right shape: a temp repository moved into place after success (`worker/fetch.rs:53`) ✅.
**Property.** Bytes become visible under their address only after verification, by an atomic rename. "Already present" means "present and verifies". A corrupt object is quarantined, not fatal.
**Against us.** On the network edge we are better: `race_fetch` verifies sha256 before it persists (`ES/p2p/blob_fetch.rs:9-15`) ✅, and the eprfs tier reader verifies every chunk and then the whole CID ✅. The eprfs tier *store* already has the right shape: its directory store writes a `NamedTempFile`, fsyncs, renames, and tests the two-writer race (`elohim/eprfs/eprfs-storage/src/lib.rs:307-343`, `durability_tests.rs`) ✅ (roadmap reconciliation), so this lesson is a `BlobStore` defect only. **On `BlobStore` we repeat Radicle's mistake in a smaller form (new finding, re-checked in source):**
- `BlobStore::write_entry` writes straight to the final path with `fs::write`, with no temp file and rename (`ES/blob_store.rs:160-172`) ✅. On a write *error* it removes the partial file, best effort (`:166-168`) ✅, so a full disk usually returns an error and leaves nothing. The case that stays open is a **crash or power loss mid-write**, and a failed cleanup.
- "Already exists" is decided by a `metadata` probe alone (`:286-299`) ✅, and that branch reports `chunk_count: 1 // TODO` (`:292`) ✅.
- `BlobStore::get` returns any non-chunked blob, including its `compute_payload_store` fallback, **without** re-hashing (`:606-624`) ✅. Non-chunked means up to `MAX_INLINE_SIZE` = 16 MiB (`:55`) ✅. Only `get_chunked` verifies the reassembled hash (`:646-651`) ✅.

So a torn inline write from a crash sits at a valid address, is served unverified, and is never repaired by a re-store, because the store reports it as already present. Remote fetchers refuse it, but they burn race budget on it every time.
**After re-genesis 1.** Landed ✅. `BlobStore` was rewritten under the byte profile (`ES/blob_store.rs:1-37`). Every file goes `tmp/<uuid>`, `sync_all`, rename, parent fsync (`:516-549`). A chunked payload writes chunks, then a dag-cbor layout record, then the marker **last**, and the marker carries the layout record's CID, so a substituted index is refused before a byte is read. `get` recomputes the whole payload's BLAKE3 before returning a byte; a mismatch moves the payload and every failing chunk to `quarantine/` and nothing is deleted. `exists` is structural, and full-hash for inline payloads. `tmp/` is emptied on open. The 16 MiB inline rule is gone: a payload is inline iff it cuts into one chunk. Verified *range* reads wait for BAO (sprint 2).
**Sprint form.** *Invariant:* write to a sibling temp path, fsync, rename; "already exists" means "exists and verifies". *a2o:* "Given a held blob truncated on disk, when a peer requests it, then this holder refuses to serve it, records it as corrupt, and re-fetches from another holder; the node keeps serving every other blob." *Tests, kept distinct:* crash mid-write (simulated by a truncated final file), `ENOSPC` (error returned, no file left), cleanup failure (a partial file left at the final path is caught by verify-on-exists).

### 4. Bind the signed publication to its lineage root and its parent from day one, at the publication envelope (R12 a)

**Failure.** Sigrefs shipped without a repository binding. `rad/root` was added in 1.1.0 "to prevent a possible reference grafting attack" (`CHANGELOG.md:926`) but required at verification only from 1.7.0. An optional `sigrefs-parent` for replay detection arrived in 1.7 (`:356`), and feature levels with downgrade detection and a configurable fetch minimum in 1.8 (`:309`). That is seven minor releases to close two attacks on the signed map ✅.
**Property.** A signed name-to-hash publication must carry, inside the signed bytes, the lineage it belongs to and the hash of its predecessor. The signature is provenance; the lineage root is a content anchor, not an authority (see the membrane).
**Against us.** The rakia release manifest binds `channelId` and carries the previous-release CID as "a HINT ONLY", verified against the channel's L2 version chain, with a mismatch as a typed refusal (`elohim/rakia/schemas/v1/release-manifest.schema.json:30-32, 296`) ✅. That is the parent half, done correctly, **in the publication envelope**. The eprfs `TierBlobManifest {epoch, record, byte_len, chunks}` is a custody record: its doc comment says it "names the closure and signer claim; accepting its witness or widening its reach remains the caller's decision" (`elohim/eprfs/eprfs-storage/src/tier_blob.rs:27-31`) ✅. Heartwood signs *mutable reference state*; an immutable artifact promoted to a second channel need not acquire a second byte manifest. So the channel and parent binding belong in the signed publication envelope, which references the byte manifest by CID, not in the byte manifest itself ◐ (a design composition, not established by Radicle). A generic artifact publication entry (R12 a) was not found in grounding ◐.
**After re-genesis 1.** The signature half landed; the lineage half did not. Every signed envelope now carries a scheme code, a multikey and the signature, and an unknown scheme is **held**, never invalid (kernel `elohim-epr` 0.2.0; shelf pick P2). brit notes moved to a versioned format, `brit.build@2` with domain `brit:build@2:` (`elohim/brit/brit-epr/src/elohim/attestation/build.rs:81-82`); historical notes stay verifiable on their frozen preimage and are never re-encoded. The channel-lineage and parent binding in a publication envelope over a channel-neutral byte manifest is still sprint 2. Steward `ChannelHead` was excluded from the crossing and still signs a hex `signature: String` (`elohim/eprfs/eprfs-peer/src/head.rs:39-40`) ✅.
**Sprint form.** *Invariant:* the artifact publication envelope's signed bytes include its channel's lineage root and its parent CID, and reference the byte manifest by full CID; the byte manifest stays channel-neutral. *Tests:* a replayed older envelope is refused as stale; an envelope signed for channel A and presented on channel B is refused as grafted; the same byte manifest published to two channels needs no second manifest.

### 5. The attestation binds the output bytes and the execution closure, and publishing it is not best-effort (R12 c)

**Failure.** The CI broker's adapter response is `Triggered{run_id, info_url}` then `Finished{result}`, with `Success`/`Failure` only and no artifact field (`CIB/adapterlib/src/lib.rs:440-455`) ✅. Artifact publication is a **long-term goal** ("We publish built artifacts, such as program binaries…", `CIB/doc/requirements.md:51-52`), and the announced metadata excludes "build log or build artifacts, at least for now" (`:83-86`) ✅. Any adapter can emit `success`, and the broker signs it with the node's device key: attribution, not proof of execution ◐. Neither result nor job update carries a workflow digest, adapter binary digest, environment or runner key; the runner is not distinguished from the node (`CIB/src/cob.rs:166-173`) ◐ (Codex CI-broker leg). The broker once recorded the node it fetched from as a change's origin, "a different node than the origin" in a distributed system (`CIB/NEWS.md:632-634`) ✅. Job COB update failures are "logged, but otherwise ignored" (`NEWS.md:247-249`) ✅. Poison events forced at-most-once processing, which leaves recovery to humans (`NEWS.md:401-409`) ✅. Other operational failures: excessive adapter output deadlocked the broker, and a queued shutdown sentinel killed the restarted broker (`NEWS.md:676-689, 746-752`) ◐; a 100-run lookup fell from 600 s to 40 s only after a fix (`:124-126`) ◐.
**Property.** The signed verdict is small, keyed to the exact input closure and execution description, and carries the output CID. Relaying an attestation changes neither its builder nor its standing. A missing attestation blocks publication rather than being logged, and each publication boundary recovers idempotently after a restart.
**Against us.** brit's `BuildAttestationContentNode` already signs `{manifest_cid, inputs_hash, output_cid, agent_id, …}` with Ed25519 (`elohim/brit/brit-build-ref/src/build_cmd.rs:72-93`) ✅ (verification pass). That is ahead of Radicle. **R12(c) is partial**: `--output <CID>` works, but nothing makes that CID a stored blob on the plane ✅. Note two different identifiers on our side: `record.output` is the raw CID of the **complete artifact** (`tier_blob.rs:29`), while the DAG-CBOR **manifest CID** is computed separately (`:213`) ✅. They address different bytes and must not be substituted for each other. Whether `rakia-executor` uses `output_cid` was not checked. ngit T5's three invariants stand; Radicle adds the best-effort anti-pattern and the relay-is-not-origin bug.
**After re-genesis 1.** Partial. Build notes are signed in the `@2` envelope with scheme and key (lesson 4). The head check that refuses an attestation whose `output_cid` differs from the byte manifest's `record.output` is sprint 2, as is routing build outputs onto the plane.
**Sprint form.** *Invariants:* the head refuses an artifact whose attestation `output_cid` differs from the byte manifest's `record.output`; the reconstructed bytes verify against `record.output` and the manifest verifies against its own CID; the attestation names the build closure (workflow and environment digest) and is signed by the runner or agent key, which is not the transport key; a failed attestation write fails the publish. *Tests:* swapping `manifest_cid` for `record.output` (and back) is refused; relaying an attestation through a third peer changes neither its builder identity nor its standing; after a restart at each publication boundary (stored, attested, custodied, head moved), recovery neither repeats execution nor loses a pending publication. *a2o:* "Given an artifact built and stored, when the attestation write fails, then the channel head does not move and the failure is a typed, durable state, not a log line."

### 6. Tighten a security floor in stages: feature levels, dual-read, adoption measured first, then a monotonic floor (inventory Stage 2)

**Failure.** 1.7.0 made `rad/root` mandatory "under the assumption that the overwhelming majority of repositories … would have this reference". In 1.7.1 it was reverted because "a larger-than-expected portion of the network is affected" (`CHANGELOG.md:341-350`) ✅. An open founder-root patch reports about 2,050 of 16,000 repositories becoming unclonable under a stricter assumption (seed patch JSON :1709) ✅.
**Property.** A security floor is a migration. Declare levels, read both forms, measure adoption, then enforce. Once a given peer has been seen at the higher level, a lower-level message from it is a downgrade, whatever the network-wide adoption.
**Against us.** Our pending instance is exact: inventory payload signatures go from Stage 1 (null byte) to Stage 2 (Ed25519) (`inventory_gossip.rs:16-17`) ✅, and the north star is "mixed versions talk; no big-bang rolls". No Stage-2 code appears in `p2p/inventory_*.rs` ✅. Whether it landed elsewhere is unverified.
**After re-genesis 1.** We did **not** take this lesson's path, on purpose. The operator ruled a clean break: inventory went from the Stage-1 placeholder straight to a signed v2 envelope on a new topic, with no dual-read and no adoption metric. That was only available because the real network is one human and every other identity is a fixture (plan §0). Read the pair together: a staged floor is the cost of having other people's nodes on the network; a clean break is a one-time option before that. Radicle's 1.7.0 to 1.7.1 revert is what spending that option late looks like. Unknown epochs and schemes are **held** rather than refused, which keeps the mechanism this lesson asks for available for the next crossing, when the clean-break option is gone.
**Sprint form.** *Design:* inventory messages carry a declared `sig_level`; receivers count peers per level as a metric; each receiver keeps a per-peer high-water level and refuses a downgrade from that peer; refusing all unsigned advertisements is a separate, later flip, gated on a measured adoption threshold. *Tests:* a mixed household (one peer at Stage 1, two at Stage 2) still converges custody; a Stage-1 message claiming to be from a peer already seen at Stage 2 is refused.

### 7. Transfer must be chunked, resumable and multi-source; a pack-oriented transfer is not (R12 d)

**Failure.** Heartwood's fetch is pack-oriented, with an enforced default cap of 500 MiB on pack receipt (`config.rs:136, 148-150`) ✅, and no interrupted-pack resume was found ◐. Whether an interruption always re-sends a whole pack is unverified without a trace ◐. The open pack-limit issue asks for a one-shot higher limit for initial clones (seed issue 4974) ◐. Q1 2025 work was still about cloning repositories over 1 GB ◐. No partial or shallow fetch (`blob:none`, `tree:0`) exists; it is an explicit unmet need (issue 10723) ◐. The third-party LFS fork stores bytes on IPFS, and its seeding still pulls whole files ⚠.
**Property.** An artifact is many independently verifiable chunks raced across holders. A peer that lands a chunk becomes a source. An interrupted fetch resumes from what verified.
**Against us.** Partially built.
- `race_fetch_with_swarm` first races **any** missing blob across peers (`race_fetch_dual`, `ES/p2p/blob_swarm.rs:432-447`), and is reached from `get_blob_or_heal` (`ES/http.rs:5484`) and `heal_blob_hash_if_absent` (`ES/p2p/mod.rs:8950`) ✅. Only a `ShardManifest` reply, the over-16 MiB case (`SINGLE_SHARD_MAX`, `ES/sharding.rs:22`), triggers the per-shard fan-out where landed shards become sources ✅. The earlier draft's "chunk-index blobs do not use racing" is withdrawn; whether chunk-granular *resume* works for them is unverified ◐.
- eprfs `FetchPolicy` has only `LocalOnly` and `FetchIfMissing` (`elohim/eprfs/eprfs-core/src/storage.rs:41-45`) ✅.
- The eprfs tier blob store is local custody: "writes only to the caller's `EprfsStorage`; it creates no network head, publication, or daemon dependency" (`tier_blob.rs:3-4`) ✅. It is generic over `EprfsStorage`, and elohim-storage already has `impl EprfsStorage for BlobStoreTier` over `BlobStore` (`ES/eprfs_tier/blob_store_tier.rs:84`) ✅, so the seam exists; no call site composes them today, and a boundary rail forbids elohim-storage depending on eprfs-storage ✅.
- On iroh there is a third physical store: `IrohBlobStore` is BLAKE3-keyed and disjoint on disk from the SHA-256 `BlobStore`, with runtime config selecting one (`ES/p2p_iroh/blob_store.rs:1-8`) ✅. In pure-iroh mode no consumer turns inventory into a byte fetch yet (`ES/p2p_iroh/inventory_fetch.rs:1-8`) ✅.
- `get_chunked` assembles the whole artifact in one `Vec` (`ES/blob_store.rs:628-655`) ✅, so serving a multi-GiB artifact costs its full size in memory.

**After re-genesis 1.** Partly landed. Chunking is FastCDC (v2020, 256 KiB / 1 MiB / 4 MiB, declared in the profile) and chunks are shared across payloads (`ES/blob_store.rs:10-17`). Shard transfer is `/elohim/shard/2.0.0` in storage and steward/node. `IrohBlobStore` is no longer a second payload store: the iroh key of a byte CID is its BLAKE3 digest, one digest with two spellings, and a pure-iroh node answers a typed `NoBytePath` rather than a silent miss (`ES/p2p_iroh/blob_store.rs:1-11`) ✅. Chunk-granular resume and the 454 MB multi-chunk round-trip named in the plan's acceptance set are **not recorded** in the re-genesis 1 journal ◐. *Sprint 2:* the sibling fetch resumes at chunk granularity and races chunks across holders (`elohim/eprfs/eprfs-peer/src/fetch.rs:1-40`; test `an_interrupted_fetch_resumes_only_missing_chunks_from_the_remaining_holder`) ✅; the 454 MB receipt (F2r) has not been run.
**Sprint form.** *a2o:* "Given a 64 MiB artifact held by two peers, when the fetch is interrupted halfway and one holder goes away, then resuming fetches only the missing chunks, from the remaining holder, and the reconstructed bytes verify against the manifest's `record.output`." Run it in each supported transport mode (libp2p, dual, pure-iroh) and report a mode that cannot deliver as a typed gap, not a pass.

### 8. Each byte plane gets its own budget; meter waste and abuse (fetch)

**Failure.** In 1.3.1 a control-message size check applied to git streams made fetches panic (`CHANGELOG.md:752`) ✅. In 1.10.0 the stream timeout became configurable (30 s default) because Tor/I2P congestion caused "spurious aborts" (`:171`) ✅. The 5 GiB data-refs limit is declared behind `dead_code` fields (`state.rs:30`, `stage.rs:365`) ✅; whether anything enforces it elsewhere is open ◐. Heartwood meters with token buckets, fetch concurrency of one per peer and announcement proof-of-work, and disconnects a peer whose inbox overfills (`radicle-node/src/wire.rs:698`) ◐ (anatomy §4, §8); abuse and amplification recur as a failure class (changelog class 10, issue 12674) ◐.
**Property.** Message ceilings, per-stream bytes, aggregate bytes, inactivity and total-duration deadlines, retries and concurrency are separate knobs. A trickle can defeat an inactivity timeout indefinitely, so both deadlines exist. Quotas apply before allocation. A losing racer is cancelled, and its bytes are counted.
**Against us.** `race_fetch` has batch parallelism 3 (`ES/http.rs:1582`) ✅. Our 1 MiB storage chunk does not bound the network frame: the blob codec's response ceiling is 64 MiB (`HARD_MAX_RESPONSE_SIZE`, `ES/p2p/blob_protocol.rs:13-16`) ✅. Winning a race does not stop the losers: `tokio::spawn` detaches each per-peer task, and dropping its handle does not abort it (`ES/p2p/blob_fetch.rs:231-240`) ✅, so racing 3 holders per chunk across a multi-GiB artifact can roughly triple transferred bytes. No per-artifact aggregate budget, distinct stall and total deadlines, retry budget or artifact-size cap was found in grounding ◐; any peer could publish an unbounded manifest.
**After re-genesis 1.** Mostly landed ✅. `FetchBudget` carries `max_bytes` (default 4 GiB), a per-peer `stall_deadline` and a `total_deadline`, and a manifest is refused before fetch when its `byte_len` exceeds `max_bytes` (`ES/p2p/blob_fetch.rs:58-93`). Racing is drop-equals-cancel: losers are aborted through an `AbortOnDrop` guard (`:184-242`). No wasted-byte metric was found by grep ◐. *Sprint 2:* the sibling fetch meters the bytes of every rejected answer as wasted and records them on the draw's `Use` event (`wasted:<n>`; test `a_chunk_that_fails_its_cid_is_metered_as_wasted_and_re_fetched`) ✅; storage's `elohim_blob_fetch_wasted_bytes_total{reason}` is on the hardening branch (H R6), not yet on dev.
**Sprint form.** *Design:* a per-artifact fetch budget (bytes, stall deadline, total deadline, retries), separate from per-chunk limits; a manifest size cap checked before allocation; drop-equals-cancel racing. *Tests:* a holder that trickles bytes is abandoned on the total deadline even though it never trips the stall deadline, and the chunk is re-raced elsewhere within budget; after a race completes, no losing task is still transferring; rejected and wasted bytes appear in a metric; an oversized manifest is refused before any chunk is fetched.

### 9. Reachability is a per-path fact; fallback across paths is part of fetch (transport)

**Failure.** NAT-class failures recur across seven or more Radicle releases (changelog class 9) ◐. 1.6 "does not know how to try a follow-up address" ◐; a peer reachable only through a relay cannot be fetched from (`radicle-protocol/src/service.rs:1677`, `:2088`) ◐ (anatomy). **Property.** An advertised address is a hint, not reachability. Path choice and fallback are a tested part of fetch.
**Against us.** The household mesh homes conductors and storage to a real iroh relay, and we run libp2p and iroh side by side ✅. That moves the problem, it does not remove it: in pure-iroh mode inventory is not yet turned into a byte fetch (lesson 7) ✅, and path selection between the two stacks is ours to get right.
**After re-genesis 1.** Unchanged. The crossing did not touch path selection.
**Sprint form.** *Test:* a chunk race in which one advertised holder is unreachable on its advertised path falls back to another path or holder within the stall deadline, in each transport mode.

**Failure.** The open issue "Versioning in Radicle" says they "run head on into the problem of versioning or the lack thereof". ### 11. Block, withdraw, retain, serve, purge and revoke are different operations (custody policy)

**Failure.** "Blocking a node stops fetching its namespace, but whatever was fetched before stays in storage, and the node keeps serving it" (open issue 4f43ad1) ✅. Its named fix is one patch, 8cb0f7e, which builds on b3c86d6; separate open block patches (19e0d56 applies the block list to announced refs, 413b3e4 refuses blocks on delegates, f708bc9) form a related series ✅. 1.7 extended blocking to connections (`CHANGELOG.md:371`) ✅. A bloom-filter TODO says bits for blocked repositories are never removed (`service.rs:2323`) ✅. For private repositories, revocation cannot recall copies, the allow list is visible to every allowed party, and a node that does not hold the repository cannot tell it is private, so it does not relay it ◐ (anatomy §9).
**Property.** Each policy effect is named per operation: acquire, advertise, route, connect, retain, serve, purge. Revocation is separate from validity: a revoked artifact stays cryptographically verifiable for history, but is no longer offered for new adoption.
**Against us.** `services/holds.rs` releases what a peer fetched for itself once nothing names it, holds what another peer placed until that peer withdraws, and never releases bytes with no arrival record ◐ (grounding §4, not re-read). If that holds, our *retain* rule is already per operation. There is no matrix for a **yanked or superseded artifact** (stop advertise? stop serve? retain for audit?).
**After re-genesis 1.** Unchanged; the operation matrix is sprint 2. One related fact: the store now quarantines and never deletes what fails verification (lesson 3), so *retain* and *serve* are already separate for corrupt bytes.
**Sprint form.** *Design:* a one-table operation matrix for `yank`, `supersede` and `revoke`, with explicit revocation semantics. The cells are decided by the channel's **standing body** (ngit T2, §12.10, and the station-6 roster question); Matthew is today's sole member of that body, not its authority. *a2o:* "Given a yanked release, when a peer asks for its chunks, then holders stop advertising it and still serve its chunks to a peer pinned to it by an older head."

### 12. Authority lineage must stay retrievable after membership changes (R12 e; ngit L1)

### 13. Divergence is an error, not a recency contest; name who elects, under which rule (R12 e)

**Failure and counter-failure.** Canonical refs first filter candidates by threshold (`quorum.rs:173`), then refuse to pick between non-linear over-threshold candidates (`quorum.rs:214`) ✅. That is right. But R1 proposed recovering sigrefs-history forks "by picking the history with the latest timestamp" (R1:487-488) ✅, and R2 admits that valid but stale identity history can be served until an honest peer shows newer history ◐. In the Unreleased section, patch merges had to switch from the identity document's threshold to "the quorum of the canonical reference rule that matches its target branch" (`CHANGELOG.md:12-16`) ✅: a rule from the wrong scope had been admitting merges.
**Property.** Two *elected* heads with no linear relation are a typed conflict for the standing body, never a clock comparison. Admission to a channel uses that channel's rule, not an unrelated quorum.
**Against us.** ngit L2 settles the doctrine. Our `ChannelHead` orders a device's own announcements by per-device `seq`, with `at` display-only (`elohim/eprfs/eprfs-peer/src/head.rs:1-6`) ✅. That is device sequencing on a steward topic, **not** release arbitration: two proposals are not necessarily two elected candidates. The release-election component is not built, and brit has no threshold-of-signers primitive for a ref ◐ (grounding §6).
**After re-genesis 1.** Unchanged; the release-election component is not built.
**Sprint form.** Name the release-election component and its authority rule (station-6 roster). *Tests:* two non-linear candidates that both qualify yield a typed divergence routed to the channel's standing body, and neither wins by `at`; when only one qualifies, it is the head; admission uses the target channel's rule, and a candidate qualifying only under another channel's rule is refused.

### 14. Identifiers must be self-describing (manifests)

**Failure.** RIPs define RIDs as a bare 20-byte SHA-1 OID (R2:265-305). Adding SHA-256 repositories needs an open patch that replaces the fixed-length RID rule with three valid forms (legacy bare SHA-1, CID-wrapped SHA-1, CID-wrapped SHA-256) and adds tests, "so RIDs stay self-describing as SHA-256 repositories appear" ("SHA-256 Repository Identifiers", revision `a82c2e55`) ✅ (seed patch JSON). Legacy bare SHA-1 stays valid; the cost is a grammar that must carry an unversioned legacy form indefinitely.
**Property.** Every reference carries its codec and hash function from the start.
**Against us.** Blob addresses are CIDv1 raw sha2-256 ✅, but `BlobStore::parse_content_address` still accepts the legacy `sha256-<hex>` form and raw 64-hex alongside CIDs (`ES/blob_store.rs:221-240`) ✅. With the iroh store keyed by BLAKE3 (lesson 7), the hash function is already plural.
**After re-genesis 1.** Landed, as a clean break ✅. Bytes are CIDv1 raw + BLAKE3-256 (`bafkr4i…`); records are dag-cbor + sha2-256; cite fingerprints stay raw + sha2-256. `BlobStore` has **no string address API**: callers decode with `ByteCid::parse` (full decode of the header, no trailing bytes, canonical re-encoding) at their own boundary, so `sha256-…`, `blake3-…` and `bafkrei…` spellings cannot reach a lookup (`ES/blob_store.rs:1-6`). `parse_content_address` and `http_blob_router.rs` are deleted. The rakia release schema pattern is `^bafkr4i[a-z2-7]{52}$` and names the legacy spellings as non-addresses (`elohim/rakia/schemas/v1/release-manifest.schema.json:92-95`). This **reverses** the R1 wording of plan §7.4 ("BLAKE3 is an allowed transport and storage hash, not an identity"): the shelf-pick amendment made raw + BLAKE3 the byte identity at epoch 0, with the profile declared in the object. Radicle's RID patch must carry an unversioned legacy SHA-1 form forever; we deleted ours, which the clean break allowed and which will not be available again (lesson 6).
**Sprint form.** *Invariant:* an artifact manifest names chunks and outputs only as full CIDs, and schema validation rejects bare hex.

### 15. A cited authority or parent is a claim; admit only what descends from the accepted root (v2, from Heartwood master 2026-11-02/06)

**Failure.** Two fixes landed on Heartwood master after this survey's snapshot (`2fce5b4e` → `8b053320`, six commits) ✅. **`eee5cb8d` "Reject COB changes with forged identity":** each COB change names an identity commit in its `Rad-Resource` trailer, and patches and issues checked the author's rights against the document in that commit, but "nothing checked that the commit is a revision of the repository identity. Any user could write a commit with a document that names them as a delegate, cite it, and act as a delegate." The fix accepts a cited document only if following parents back from `rad/id` reaches it. **`df62b66d` "Keep only the root's applied descendants in a history":** loading an object kept every entry reachable from its refs, including entries that did not descend from the root; "they were never applied, but they were tips, so the next honest update used them as parents. Any user could thus make a delegate's change to one object also apply to another." Evaluation now requires a parentless root, keeps only the root's descendants, and applies an entry only when every parent was applied. A third commit, **`783b06fb` "Keep rad/id at the current identity"**, fixed a derived pointer that every caller had to move itself and one path forgot.
**Property.** Citing an authority is a claim about lineage, not evidence of it: the cited document must be checked as a member of the accepted chain. An object's history is what descends from its root, and an entry that is present but unapplied must never become a parent of an honest one. A derived pointer has one writer.
**Against us.** The rakia release manifest already treats the previous-release CID as a hint verified against the channel's version chain (lesson 4) ✅. The custody follow-ups from re-genesis 1 name the same class on our side: "reject conflicting alias bindings" and "cross-signed agent↔transport bindings before custody rows read as verified possession" (`genesis/docs/superpowers/sprints/2026-11-05-regenesis-1/RESULT.md`) ✅. Whether accountable-correction successors, brit note chains and the planned release election check that a cited predecessor is in the accepted chain, rather than only well formed, is unverified ◐. The "one writer" half matches a device-runtime finding already in the `dataplane-convergence` ledger (one superseding disk writer for the runtime manifest, DELTA 2026-10-25-M) ◐.
**Sprint form.** *Tests (sprint 2, release channel and correction chains):* an envelope that cites a parent outside the channel's accepted chain is refused as a graft, even when the parent is well formed and signed; an entry whose parent was refused is refused with it and is never used as a parent; a correction or successor citing an authority revision that is not an accepted revision of that record's root is refused.

### Answers to the questions v2 left open

- **Lesson 1 / T1: custody before head.** It is **not a gate anywhere in sprint 2.** The sibling fetch moves no head: at `self`/`intimate` reach a custody pledge has zero DHT heads (D6), so there is nothing for custody to gate yet. The rule is specified as a story only: `artifact-custody.feature` elects under Trusted reach only with a versioned custody policy, holds an unknown policy epoch as `pending-election`, names a shortfall and its repair, and makes "no eligible head" explicit. T1 stays **open** and moves to the release plane (F5). **"A fetched artifact is not served onward" is the floor on dev, and it is structural** ✅. The mount indexes only this device's own `custody-blob` Produce with `copy:self` and no `via:` slot (`blob_mount.rs:782`, test `a_folded_sibling_produce_never_indexes_a_manifest`); a fetch records a `Use` (`fetch.rs:21-23`), never a custody Produce. For rakia objects this is the intended floor: possession is not custody, and becoming a holder must be an explicit, counted act (a verified put that writes the custody Produce), never inferred from having drawn the bytes. That adoption act is designed, not built.
- **Lesson 4 / T3: where the lineage root and parent binding live.** In the **release manifest**, not in the `DerivationRecord` or the brit note. A `DerivationRecord` binds one derivation, `(method CID, input) → output`, and stays true whoever publishes it. A brit `@2` note is one device's signed attestation of one build. Neither knows a channel. A release manifest is where a channel's lineage is already checked (its previous-release CID is verified against the channel's version chain, lesson 4) and where an artifact's output CID becomes a release. So the publication envelope carries the genesis CID and the parent, and cites the derivation's output; this is the shape F5 inherits. Sprint 2 built none of it (T3 stays half).
- **Lesson 5 / T6: the swap test and the attestation chain.** Done for the sibling path ✅. `epr artifact put` writes the method descriptor under its CID, records the brit attestation with `brit-build-ref build put --output <byte CID> --inputs-hash <key CID>` (`artifact.rs:1174-1176`), and writes one custody Produce that is also the `artifact-produce@1` crossing record. The consumer refuses any manifest that is not the one the crossed record named, whose record `key` is not the key it computed itself, or whose `output` is not the output asked (`fetch.rs:6-10`); the story covers the swap in both directions. **The key is the labelled interim:** `KeyInput::Raw(<closure CID>)` over the descriptor's view at HEAD, recorded as `basis-key:git-tree` (`artifact.rs:15-23`), one function for producer and consumer; the key also binds the resolved compiler and linker (path and `--version` CID under the recorded `PATH`). **F1r must deliver** a real projected view (`KeyInput::Projected`, so `gate-task.mjs` stops handing ark closure metadata) and the live two-device reuse receipt (`basis: Computed`, `independence: sibling`). Neither was run.
- **Lessons 7 and 9: transfer, resume and paths.** Done on dev for one steward's devices ✅ (`fetch.rs:1-35`). The manifest comes first and is size-capped before any chunk moves; chunks already held are not asked again (resume); missing chunks are raced round-robin across holders under a per-chunk stall bound and one total deadline, with a refused, stalled or corrupt holder abandoned and its chunk re-queued; every chunk is verified by CID and length, the whole by BLAKE3 at install; wasted bytes are metered. One connection per holder carries one artifact, so a holder records one `serve-blob` session, not one per chunk. Over a relay-only path an answer must arrive at no less than one 4 MiB frame per 10 s, else the fetch ends as `TransportCannotDeliver` (`fetch.rs:196-198, 362-385`); every other non-install is a typed `FetchGap` and the build proceeds locally. Against Radicle's pack: a pack is one stream per fetch that restarts whole; ours restarts per chunk and per holder. **F2r must prove:** the 454 MB storage binary arrives byte-identical (b3sum on both devices) faster than a local rebuild; the chunk count and the fraction shared with the previous binary; an interrupted real fetch resumes only missing chunks; and per transport mode, iroh direct measured, relay measured or `TransportCannotDeliver`, libp2p and dual as typed gaps. First compare both devices' `tool:` key lines, or the keys will differ.
- **Lesson 11: yank, supersede and revoke.** Partly ✅. Serving is scoped per method by an explicit grant list (`berth.artifacts.serves`, `ArtifactServeList`); removing a grant stops serving without deleting bytes or evidence, and a malformed policy reload fails closed. Supersession is by event order: for each output only the manifest of the latest own custody event in log order is served, and replacing an entry removes every membership the replaced manifest gave its objects (`blob_mount.rs:135-150`; the Codex review's first high finding was exactly that leak, fixed before landing). An admitted device outside the grant gets a named refusal; a stranger gets one uniform refusal whether the artifact is granted, held or unknown. **Not built:** purge, release yank, and consent withdrawal as a lifecycle act (the story specifies them).
- **Lessons 12 and 13: standing, bindings, election.** For sibling artifacts, standing is the person's: only the steward's own enrolled devices are admitted, and the grant narrows what each may draw. The H track (on the storage closure) makes a custody holder an authenticated agent: authority only from a cross-signed binding the DHT has confirmed, gossip-arrived bindings as hints, well-signed claims from an unbound author held (bounded) and replayed when its binding confirms, and supersession on the signed core so a superseded binding stays superseded under any fresh anchor. **Open (filed, not gating):** first-writer-wins on the unsigned DHT anchor; confirmations never re-checked, with no maximum validity and revocations not joined (lesson 12's retrievable-lineage question); and the DNA-level Sybil residual, ruled by the operator not to gate ("our sybil resistance doesn't have to be perfect yet"; `arch-dataplane-borrows-backlog.md` row 25). **Lesson 13:** two outputs for one derivation key are a typed `Mismatch` and nothing is fetched (`fetch.rs:1245-1268`) ✅, our first typed divergence; who elects a release head remains open with T7.
- **Lesson 15 on our side.** Two of its three classes are closed where sprint 2 touched them: the revival class for bindings (supersession on the signed core, H pass 4, on the storage closure) and the foreign-entry class for serving (a folded or sibling Produce never becomes serving authority, and a replaced manifest keeps no membership). Correction and successor chains and the release election are unverified or unbuilt ◐.
- **B1: are we past it?** **On one steward's devices, for the case it covers, yes:** large artifacts move outside git, chunked, resumable, multi-holder, verified per chunk and whole, with the waste metered, pending F2r's measurement at 454 MB. **For cross-steward rakia objects, not yet.** What remains: grants beyond one person's devices (a carrier's task view, F4, then community reach); custody counted and repaired before a head moves (T1); the release election (T7) and the lineage-bound envelope (T3); one payload store per device (E4) and the FsStore ruling (R1.4); bao range reads; and tier transport over libp2p and dual.

Rakia is our build planner and executor. Its release manifests are what becomes a channel head when an artifact moves from one steward's devices to a community. ## Addendum — for Radicle: how Elohim is approaching the deeper primitives (2026-11-08)

*Written for a reader from the Radicle project, by the Elohim project (drafted by agents working for the project's steward, human:matthew, and the steward's to review). It is offered in kind. This survey read your code, changelog, RIPs and disclosures closely and took more from them than from any other peer we studied. This section returns the favour: what we built after reading you, what we took, what we did differently and why, and what is not proven yet. Each claim names its evidence in our repository. None of it is a request to adopt anything.*

**Who we are, briefly.** Elohim is a protocol for communities to hold content, value and governance together, built on Holochain for signed, validated shared state, with a separate peer-to-peer byte plane (libp2p and iroh) for blobs and build artifacts. Our developers' workspaces are themselves peers. A workspace that needs a binary another of the same person's devices already built fetches it, verified, instead of rebuilding it. That is the artifact store this survey was written for. We share your instincts: verify before apply, sign state, never trust a payload's claim about itself. We differ on one premise, stated under **Membrane** above. A key signature is provenance. Standing belongs to people and their communities, and the network, not a device, holds the root.

**On trust in general.** Radicle aims at self-certification: verify every signature against the delegate set and trust nothing else. We share the verification. We design for a **trustful** network rather than a trustless one. Gates check every claim. Trust is earned and lags delivery: a claim starts amber and becomes green on evidence. Authority comes from the diversity of the network and the validation of claims, never from holding keys, compute or a server. A trustless profile is one setting we can run at an edge, not the default.

### Primitives, and what we learned building them

1. **A byte address declares its profile.** Every byte address is a CIDv1 whose codec and multihash name the hash (raw + BLAKE3-256, `bafkr4i…`). The chunker (FastCDC with stated sizes) and the erasure code are declared in a profile carried by the object. Records are dag-cbor + sha2-256, and parsers refuse anything they cannot decode exactly. We crossed from a bare `sha256-` string to this in one clean break (re-genesis 1, above). *What we learned from you:* RIDs began as bare SHA-1 and carry that form forever (lesson 14). *What we would offer:* when the address says which hash and which chunking produced it, the next hash change is a profile choice rather than a network partition. *Honest limit:* we could break cleanly only because our live network is one human's devices plus fixtures. The next crossing will need the staged floor your 1.7.0 → 1.7.1 revert taught (lesson 6).

2. **A build output is a derivation, not a file.** An artifact is named by a derivation key, the method's content address together with the input closure's, and by the output's byte CID. The build attestation's `inputs_hash` is that key's CID. A consumer recomputes the key itself. It refuses a manifest keyed for another closure, and treats two holders disagreeing about one key's output as a typed mismatch, never a recency contest (`elohim/eprfs/eprfs-peer/tests/fetch.rs`, `serve_blob.rs`). *What we would offer:* your CI broker's results carry no output digest (lesson 5). A CI result that names its closure key and its output CID can be reused by any peer that computes the same key, so CI can be shared instead of re-run.

3. **Custody is a continuing contract with evidence, not a replica count.** Our custody counts read only holder rows that are bound to an authenticated identity, witnessed and fresh. Unbound but well-signed claims are **held**: neither counted nor dropped. At private reach, custody is a pledge that creates no shared-state entries at all (`genesis/a2o/features/storage/artifact-custody.feature`; hardening on branch `artifact-store/h`). *What we learned from you:* `DEFAULT_REPLICATION_FACTOR = 3` is reached once and never held, and this is still the survey's first lesson. *What we would offer:* a repair loop has to read the same evidence the publish decision read. Otherwise "seeded" drifts from "held".

4. **A holder claim inside a payload is bound to the identity the transport authenticated.** Inventory gossip admits a message only when the gossip layer's authenticated source equals the claimed author and the signing key is the one that peer embeds. Agent-level authority additionally requires a binding that is both cross-signed and confirmed in the shared DHT. Your 2026-09-23 disclosure is about the handshake. We had the same class **one layer up**, in identities declared inside payloads, and found it while reading you (lesson 2). *What we would offer:* when iroh fixes the handshake, payload-declared Node IDs in announcements still need binding to the authenticated peer, or the impersonation moves up a layer. *Honest limit:* our bindings are not yet Sybil-resistant. One binding costs one DHT entry. The steward ruled that Sybil resistance does not have to be perfect yet, and the gap is named in our security backlog, not closed.

5. **Serving is scoped to a grant, and refusal reveals nothing.** A device serves an artifact only under a grant for its method, by default to no one. A device outside the grant gets a typed reason. A stranger gets one byte-identical refusal whether the artifact is granted, held but ungranted, or unknown. A policy reload that drops a device refuses its next chunk on a connection that is already open (`elohim/eprfs/eprfs-peer/src/serves.rs`, `blob_mount.rs`). *What we would offer:* for private repositories, an allow-list of nodes says who may connect, not what each may read. Per-object scope with a uniform refusal removes the "do you have it?" oracle.

6. **The unknown is held, not refused or guessed.** An unknown epoch, signature scheme or custody-policy version is held with its reason, so a newer writer's data reaches an older reader without being refused or misread. Unknown record extensions keep their bytes and their CID through a fetch. *What we learned from you:* feature levels and dual-read before a floor (lesson 6).

7. **Retry on the event, never on a tick or a boot snapshot.** Our worst night on the alpha fleet came from code that captured a conductor client once at boot, and from a binding minter that gave up after six tries before the conductors existed. Both now acquire lazily, retry for the life of the process, and wake on the connect event. *What we learned from you:* a fetch with no seed waits for the periodic tick rather than the seed's arrival (lesson 1). We had the same shape and paid for it.

8. **Admit only what descends from the accepted root.** We took this from your week of 2026-11-02 (`eee5cb8d`, `df62b66d`; lesson 15). At device scope the sibling fetch already insists that the served manifest is the CID the holder's crossed record named, and that the record's key equals the locally computed key. A superseded binding core stays superseded under any fresh anchor. Whether every correction chain and our future release election check membership in the accepted chain, rather than only form, is **not verified yet**.

### What we have not done

- No release election and no threshold-elected channel heads in production. Your canonical-branch election is ahead of us there (lesson 13).
- No serving across stewards. Carriers and a second person's admission are reserved in the grant vocabulary and grant nothing until they have a verifier.
- The large-artifact case is in code (chunked, verified per chunk and whole, resumable, budgeted, raced across holders) but its 454 MB receipt between two real devices is still owed.
- One payload store per device is designed, not built.
- Everything above runs on one steward's devices and a test fleet, not on a network of independent people. Radicle has run that network for years.

### What Radicle might take away, if anything

Offered as a reading, not advice:
- a declared byte profile before 2.0's transport change, so hash agility rides the same partition;
- output digests and closure keys in CI results;
- binding payload-declared Node IDs to the authenticated peer after the iroh handshake lands;
- per-object serving scope with a uniform refusal for private repositories;
- a repair loop that reads the same evidence as the publish decision.

Where we diverge on identity, we diverge on purpose (see **Membrane**). Where we converge, much of the convergence came from reading your code and your changelog's honest failure descriptions. Thank you for writing them down.
