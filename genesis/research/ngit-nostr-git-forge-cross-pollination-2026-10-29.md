# ngit Cross-Pollination — October 2026

**[ngit](https://ngit.dev)** is DanConwayDev's protocol family for *"Git collaboration, without the platform"*. It splits a git repository into **state** (refs, maintainer-signed, replicated as Nostr events across relays — *"the source of truth"*) and **data** (git objects on ordinary git servers — *"interchangeable storage… the git server is no longer authoritative, it's a cache"*). Around that split sit four small protocols, each with more than one implementation: **NIP-34** (repo announcements, ref state, patches, PRs, issues, status), **GRASP** (relay + git-smart-HTTP hosting authorised by signed state), **NIP-C1 Nostr CI** (coordinator / compute-provider / runner roles with signed results) and **NIP-82 + ncontainer** (releases and OCI tags as signed mutable pointers over SHA-256 blobs on Blossom). The v3 family (ngit 3.0.x, ngit-grasp 3.0.x, ngit-ci 0.1, GitWorkshop 4) shipped in September 2026.

The one-line verdict (revised after the challenge pass): **ngit is daily-driven because it does not replace git.** People keep stock git porcelain; a standard remote helper (`git-remote-nostr`) carries the signed authority state and checks pushes against the state it last read; a small CLI owns only the social and evidence objects, with `--json` and an `--offline` cache; and GRASP hosts serve exactly the refs that signed events justify. That is the lesson brit needed and the first draft missed: it read ngit only as a forge-authority exhibit and ranked forge objects as brit's next work, when brit could not yet open our own monorepo and its evidence reads did not fail closed. **ngit's forge vocabulary is mostly already ours in other terms or owned by the closure-keyed landing plane; what we take is the daily-use shape, and what we leave is the keypair as a repository's root and signer-clock ordering.**

The first draft's verdict, kept for the record and corrected in the sections below: *"It ships the forge layer … that our family has designed but not yet shipped. Its weakness is the substrate under the cut: authority is a bare keypair, ordering is the signer's own `created_at`, conflicts resolve by last-writer-wins, and relays validate nothing beyond signature and tag shape."* The last clause was wrong for GRASP hosts, and the CAS contrast was overstated (see [Challenge pass](#challenge-pass--what-changed-and-why)).

Method: five ngit repos shallow-cloned from `https://ngit.dev/<repo>.git` (`ngit-docs`, `ngit`, `ngit-grasp`, `grasp`, `ngit-ci`) and read directly — the docs repo carries the full NIP-34 text with the maintainer proposal (PR #2324 @ `f014c924bfa8`), GRASP-01…08, and NIP-C1 (ngit-ci @ `570218745caa`). Our side was mapped by a read-only grounding pass over brit, rakia and the epr tree; synthesis by the orchestrating session. The draft was then put through a 41-agent challenge pass (five grounding readers including a fact-check of every ngit claim against source, twelve challenge items read through the p2p-design-gate, gradient-reading and local-first lenses, two adversarial skeptics each) and a design panel (Opus, Sonnet and Codex designs, three Codex code probes, two Claude judges) that produced the brit daily-driver sprint. **Verification key:** ✅ verified in primary source · ◐ single-source / plausible · ⚠ web-only or roadmap claim.

## ⚠️ Name / lineage guard (read first)

- **ngit ≠ the generic "nostr git" idea.** ngit is one implementation family (ngit CLI + `git-remote-nostr`, ngit-grasp, ngit-ci, GitWorkshop) maintained in tandem by one author; NIP-34 and GRASP are the shared protocols and have other implementations ✅ (`docs/why-ngit.md`, `docs/v3.md`). Cite the protocols for shape, ngit for shipped behaviour.
- **Draft status everywhere.** NIP-34 is `draft optional`; the maintainer model is an unmerged NIP PR (#2324); NIP-C1 is `draft`; ncontainer is a draft ✅. Stability claims are about ngit's implementation, not the standards.
- **Maturity.** ngit 3.0.5, ngit-grasp 3.0.10 (Cargo.toml) ✅; Rust, `git2` + `nostr-sdk 0.45`, MIT. The CI marketplace, hosted private services and server-side moderation are roadmap ⚠ (`docs/roadmap.md`).

## Anatomy

### 1. The cut: state on relays, objects on git servers ✅

A `nostr://<npub>/<relay-hint>/<identifier>` URL resolves through `git-remote-nostr` (a standard git remote helper): read current ref state from relays, fetch matching objects from any `clone` URL in the announcement. A maintainer can add, drop or swap object hosts without contributors changing remotes (`docs/how-it-works.md`). Mirroring to GitHub is either a manual remote ngit never learns about, or an `--additional-clone` listing that `ngit sync` keeps aligned. Only a logged-in maintainer's `ngit sync` (never fetch or push) may adopt a listed forge's tip and sign new state, and only when the forge is strictly fast-forward ahead and its domain is explicitly trusted (`docs/repositories/mirroring.md:84-97`). The remote helper advertises the cached signed state for `list for-push` and refuses a ref that is out of sync with it (`git_remote_helper/list.rs:43`, `push.rs:150-155, 1338`); v3 adds `--force-with-lease`. GRASP pushes are always forced and the host compares only the new oid with the latest signed state, so the fast-forward check is **client-side, against the client's own view**.

### 2. NIP-34 event model ✅

| Event | Kind | Shape that matters to us |
|---|---:|---|
| Repo announcement | 30617 (addressable `(kind,pubkey,d)`) | `clone`/`relays` lists; `r <euc>` = earliest unique commit, the fork-grouping key; roles `M` (lead), `m` (co-maintainer), `o` (moderator) with start/end timestamp history |
| Repo state | 30618 (addressable) | `refs/heads/*`, `refs/tags/*` → commit id; `HEAD` |
| Patch | 1617 | `git format-patch` body; optional commit/parent/committer tags so the applied commit id is stable |
| Pull request | 1618 | tip `c`, `clone` URLs where the tip is pushed to `refs/nostr/<event-id>`, `merge-base`, labels |
| PR update | 1619 | new tip for an existing PR (NIP-22 threading) |
| Issue | 1621 | markdown thread with subject and labels |
| Status | 1630–1633 | Open / Applied-Merged-Resolved / Closed / Draft; merge carries `merge-commit` or `applied-as-commits` |
| User GRASP list | 10317 | preferred hosting services, like a relay list |

Two rules carry the authority model: **only members' events are authoritative**, and **the most recent Status by `created_at`** from the root author or an authorised member wins. Addressable announcements merge by *greatest `created_at`, lowest event id as tie-break*, except `clone`/`relays`, which are unioned across members (`protocol/nip-34/specification.md`).

### 3. Maintainer authority — the v3 breaking change ✅

A repository is a **recursive, reciprocal set of announcements** sharing one `d` tag (the "virtual repository"). Before v3, *listing* someone made their state authoritative — an invitee's ordinary push to their own fork could silently replace the inviting repo's refs, with no force-push anywhere. v3 makes listing an **invitation only**; authority starts when the invitee publishes acceptance (`ngit repo accept`), and acceptance is never a side effect of another command. An explicit lead (`M`) coordinates the roster but has **no stronger git authority** than any confirmed co-maintainer; moderators (`o`) manage collaboration without authority over git state; leaving (ending one's own role) beats any third-party assignment; history conflicts resolve by the selected maintainer's record, then shortest recursion distance (`docs/v3/maintainer-model.md`). They shipped this as a coordinated SemVer major across client, server and web UI because *"even a temporary difference [in who is authoritative] deserves an explicit compatibility break."*

### 4. GRASP — hosting authorised by signed state ✅

GRASP-01 (required): one service is both a NIP-01 relay and a git smart-HTTP server at `/<npub>/<id>.git`. It **accepts pushes only if they match the latest state announcement, respecting the recursive maintainer set** — the signed event pre-authorises the push; there is no forge account. New announcements, state and PRs sit in **purgatory** ("won't be served until git data arrives", discarded after 30 min). PR tips land at `refs/nostr/<event-id>`; the spec says they SHOULD be deleted if no matching PR event arrives within 20 min, and ngit-grasp in fact applies its 30-min purgatory expiry to them (`ngit-grasp/src/purgatory/mod.rs:549-558`). GRASP-01 requires the `allow-tip-sha1-in-want`, `allow-reachable-sha1-in-want` and `filter` capabilities and permits `blob:none` / `tree:0` filters, which make partial clones cheap for web clients. ngit-grasp also **reconciles the refs it serves so they are "exactly those justified by accepted State, PR, and PR Update events"** (`git/authorization_integrity.rs:1-6`), rejects state events from authors outside the recursive maintainer set (`nostr/policy/state.rs:96-142`), and keeps an object-staging invariant: *absence of a ref never proves history disposable* (`git/staging.rs:1-17`). Extensions: **02** proactive sync of events and missing git data from the other listed hosts (≥ hourly); **03** sync of the full conversation history via the outbox model; **05** archive/mirror of repos that don't list the service; **06** fork-free PR hosting at `/prs/<npub>/<id>.git` when the target's own hosts refuse; **08** private repos — NIP-42 relay auth and a repo-scoped NIP-98 credential on every git request, a service-wide pubkey whitelist, an encrypted (NIP-44) list of one's private services, and the candid boundary *"whitelist membership controls access only… authorized users and the server can copy and republish"* (`grasp/*.md`, `docs/repositories/private.md`).

### 5. NIP-C1 Nostr CI — three roles, signed provenance ✅

**Coordinator** (observes repo activity, applies admission policy, selects workflows, holds secrets, signs progress and the combined Workflow Result), **compute provider** (executes one job and signs its Job Result — *"the provider asserts only the job execution"*), **runner** (the workflow-format engine: `act` today, a Nix/Firecracker runner experimental ⚠). Results bind `c` commit, `w <path> <sha256-of-workflow-file>`, normalised trigger `o`, and per-file `artifact` tags whose Blossom URL embeds the sha256 — *"the compute provider's commitment to the exact bytes produced"*. Admission is explicit (`M operator-selected|maintainer-request|open`, `X automatic|request-required`); unknown policy values must never be read as open or free. A Manual Trigger is an authorised replay of an exact workflow hash; Workflow Progress and Workflow Result MUST quote the request, Job Results MAY. Secrets go maintainer → coordinator as ephemeral NIP-44 events to a rotating recipient key that never touches disk, with ordering tombstones so an old `set` cannot resurrect a removed value; release to a job re-checks current maintainership at run time. The roadmap's money line: *"Paying for compute never makes its answer true. Signed provenance and each participant's explicit trust policy remain essential."* ⚠ (marketplace unshipped). Released v0.1.1 keeps coordinator and provider in one deployment; ngit-ci HEAD `f5818c1` (unreleased) already has a native-Nix path with separate coordinator, discovery, provider and adapter identities and adds Compute Provider Advertisement (39845) and Job Allocation (9845) (`ngit-ci/CHANGELOG.md:12-27`, `NIP.md:17-33`). Two caveats the first draft missed: secret ordering is itself `created_at` last-writer-wins (`spec:165`), and the bunker binding stays coordinator-readable (`spec:173`). ngit also has an opt-in merge gate, `ngit pr merge --require-ci-trust`, because *"a successful push does not enforce CI by itself"* (`docs/ci.md:198-224`) (`protocol/ci/specification.md`, `docs/roadmap.md`).

### 6. Releases and containers — mutable signed pointers over immutable blobs ✅

NIP-82: application (32267) → release (30063: version, channel, authoritative asset list) → asset (3063: sha256, media type, platform). ncontainer (30624) maps OCI tags (`latest`, `1.4.2`) to manifest digests; a read-only OCI Distribution gateway serves verified blobs to Docker/Podman. *"Container tags remain mutable signed project state while every image blob stays content-addressed."* Publishing requires a confirmed repository maintainer. `.ngit/release.yaml` is a committed, strict-schema manifest (unknown fields rejected) (`protocol/software-publishing.md`, `docs/releases/manifest.md`).

### 7. Agent and key ergonomics ✅

Signer secrets moved out of git config into the OS credential store in v3, reflecting *"a changed threat model in which coding agents and other tools routinely inspect Git config"* (`docs/v3.md:147-151`) — incidental disclosure, not targeted compromise; the fallback is a user-only file outside any repo, and plaintext git-config storage remains an explicit opt-in; NIP-46 remote signers keep the key on another device; `--signer` fails closed on an ambiguous selector. `ngit skill install` drops a managed agent skill into the repo, uncommitted, so normal validation runs; every command has `--json` with exactly one JSON document on stdout and diagnostics on stderr; `--offline` reads a local event cache (`docs/accounts.md`, `docs/agents/index.md`).

## Challenge pass — what changed and why

The first draft's verdicts were put through twelve challenge items, each read through the p2p-design-gate, gradient-reading and local-first lenses and attacked by two skeptics, plus a fact-check of every ngit claim against source. Three things changed the picture:

1. **The daily-use lesson was missing (C12).** The draft asked what ngit's forge objects could give brit and never asked why people use ngit every day. The answer is that it composes with stock git instead of replacing it. brit, meanwhile, could not open our monorepo, refused `add` under the workspace's global LFS configuration, and read its own evidence without checking signatures. Forge objects were the wrong next work.
2. **The two sharpest leaves were overstated.** GRASP hosts do enforce authority (push authorization against the maintainer set, served refs reconciled to signed events), and ngit's client does check fast-forward against its own view. The honest contrast is narrower: ngit's signed state carries no expected prior, so two maintainers who read the same state can both pass their local check and the later `created_at` wins.
3. **Most forge takes were already ours, or already owned.** The closure-keyed landing plane (`2026-10-29-closure-keyed-landing-plane-design.md`, Draft, another session) owns landing intents as `Intent` atoms, the Change-Id hook, the Phase V/L pre-push split, sibling verdict reuse, device-written brit `ci:` notes, the A7b bundle carrier and brit distribution off GitHub. The elected-content spec (`2026-09-01-runtime-artifacts-elected-content-design.md` §12.1) had already answered "is a branch a channel". This survey feeds those homes; it does not open parallel ones.

## Export direction (revised)

What we still have that ngit lacks: a root whose inviolability comes from the **diversity** of a socially-derived holon (independent kinds of relationship — school, neighbour, family, NGO, government, association, workplace, library — not a set of keys; ngit's maintainer roster is a headcount of keys, and keys are free to mint); elected heads instead of signer-clock ordering; verification in the receiver's own conductor; N-of-M **diverse** attestation in which the builder's own never counts; release soak and rollout waves; standing distinct from key possession. What ngit has that our SCM plane lacked until this sprint: hosts and readers that serve only what signatures justify, a CLI with one JSON document per command, and a client that coexists with git.

## Questions for the design review — answered

### Questions for the epr / brit / rakia design review

1. **Is a git branch a rakia channel?** Proposal: `refs/heads/<b>` of repo *R* is the channel head `scm:<R>:<b>`, moved by CAS with an expected prior and elected by standing. That gives brit's `BranchContentNode` its authority without a new DHT entry type (through-line :105) and with no per-commit heads. It reuses T3's purgatory for "announced, bytes not yet here".
2. **Where do proposals and social objects live?** This is the handoff's open question. ngit's evidence: social objects are signed records **separate from git refs**, collected by the hosting tier (GRASP-03) rather than by every client. That favours **typed epr records on the steward space, with brit notes as the degraded transport**, which is the handoff's own *"one replication substrate, social objects next to code"*.
3. **The maintainer roster's home.** Is it the epr participants roster, Mishpat's `CouncilRoster`, or a brit stewardship record? Whichever holds it needs T2's invitation → acceptance boundary, role intervals, and a moderator role without ref authority.
4. **What does the serving tier speak?** `bundle:<cid>` over the eprfs tier (A7b), git smart-HTTP for ordinary git clients, or both? If smart-HTTP, take GRASP-01's partial-clone advertisements (`filter`, `blob:none`, `tree:0`). A web reader depends on them.
5. **The rung-1 CI attestation schema.** Adopt T5's binding (commit, workflow-file hash, normalised trigger, per-artifact hash) and its two-signer split (coordinator vs provider) in the brit build note before Canopy, so local and peer verdicts share one shape.
6. **Retire the per-clone `AgentKey`** in favour of the device key (T7).
7. **Lockstep audit (L3).** Which of our authority rules are evaluated per client today, so that changing one would need every client to upgrade together? Each one is a candidate to move into integrity validation.
